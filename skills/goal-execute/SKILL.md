# Goal 连续执行

创建和恢复统一使用 schema 3。当前接手者负责实现、集成和交付；流程、短提示及资源分工见 `references/delivery/agent-delivery-flow.md`。

## 接手与推进

1. 首次读项目 README、AGENTS、CLAUDE 及最新授权；恢复只补相关变化。默认当前目录和现有环境，不主动创建或切换 worktree，Git 写操作按 `references/git-safety.md`。
2. 明确同一需求的 `.goal/goal.yaml`、`status.yaml`，读取 `references/delivery/goal-v3.md` 并运行检查器。核实实际改动、仍有文件/资源操作权的参与者及必要现场；旧摘要不能证明当前通过。
3. 选择下一可执行动作：先吸收用户修订、核实现场分歧、解决高影响未知、接回成果，再推进必需结果。长任务的 `status.yaml` `next_action` 只能含一段，并写明要打开的技能名、做完留下的记录和停止条件。包含多段，或缺少其中任一项时，先改好 `next_action`，再写代码。开始该段前，第一个动作是读取 `next_action` 点名的技能，本次只做这一段。使用场景、服务端模拟、前端交互和真实业务不写进同一步。普通自测通过只说明可以改写下一段 `next_action`，不说明整组完成，也不在同一次继续里顺手做下一段。下一段开始前，先读取新的 `next_action` 点名的技能。首条真实路径不自动 CR；正式核验按 `references/stages/review.md` 合批。
4. 在已有边界依 `references/delivery/execution-evidence.md` 判断时间/token 消耗是否带来进展；缩减重复读取、过度委派和无新信息的检查，不降低质量或扩大授权。

按原型还原的界面在首次执行、恢复及换实现者时，都复用原型阶段已确认的图片版本和路径。按 `references/delivery/evidence-driven-delivery.md` 的三阶段图片基准交接，缺失或错图回原型准备环节；不能由接续实现者临时截图当基准，也不能以实现快照更新代替对图验收。已有同版确认和未受影响证据直接复用，不重新让用户逐图审批。

有确认原型的前端/API 工作，首次执行和恢复都核实本组前端体验、领域/API 契约和模拟替换的实际进展，按 `references/plan/task-breakdown.md` 继续；不因恢复丢失前端先行顺序，也不重做已有效完成的阶段。接口协议和使用场景以方案为准，不在实现时重定。服务端先按方案用模拟数据做入口，前端只取数据、提交、展示错误。方案没写使用场景，或入口还没有服务端模拟时，不把筛选、默认选中、保存后读回写进各前端。服务端按领域职责及依赖实现。本组进入真实后端或复用布局前，以 `references/stages/review.md` 为准：现有记录里要有每个动作点完后页面变了什么，并完成该规则的“前端体验放行前的覆盖核对”；status的done和报告的通过标题不能代替覆盖关系。没有这个差异，或浏览器打不开时只读了源码，就停在本组，不把真实保存叫做探针。一个端的问题要查其他端和共用组件。单测、Mock、真实接口、实际页面分开写。

用户只要求检查或只跑一项时遵守范围；默认按 `next_action` 一段一段推进。每段做完只写好下一段 `next_action` 后停止；下次继续时先读取该段点名的技能，再开始该段。开工条件见 `references/stages/goal-handoff.md`。不支持格式不得改版本号伪造迁移；轻量工作不建 Goal。

## 协作与收尾

派发默认最小显式上下文，保留当前来源、最近决定、授权和操作范围，不按节点配齐 Agent。主执行者不只转发消息。独立验证先形成预期并观察，再读实现结论及代码；同一独立 Agent 可合并验收和 CR。

共享进程、端口、数据库和配置由明确操作者安排；测试也按副作用判断。待验范围及其依赖冻结，独立工作继续。失联参与者未核实释放前不能抢占范围。局部隔离保留真实能力和回收检查，TODO 不代表完成。

完成时汇集全部必需结果、最后差异与有效证据，核对用户实际入口，准确区分开发验收与发布。只在创建/恢复、正式核验和收尾使用检查器与必要快照，不每个小动作重复登记。

App Goal 仅作可选镜像；仅在用户明确请求且工具契约允许时创建，不覆盖其他目标，不凭空设置预算。规则采用不授予提交、安装、外部写入或发布权限。
