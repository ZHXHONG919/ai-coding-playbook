# 共用交付行为回归

这里保存与格式版本解耦的共用交付行为场景；涉及 Goal 的现行输入与预期统一采用 v3。样例使用脱敏简化情境，不含业务项目数据；准备样例不等于已经通过验证。

## 区分证据类型

| 类型 | 实际做了什么 | 能支持的结论 | 不能支持的结论 |
| --- | --- | --- | --- |
| 场景推演 | Agent 阅读输入，判断路由、下一动作和禁止行为 | 在给定上下文中的规则理解和取舍 | 已实际实现、真实工具成功、交付质量或成本改善 |
| 真实执行 | 在隔离工作区执行实现、验证、审查或恢复，保留实际动作和产物 | 对应版本、环境和场景中的实际执行结果 | 未运行环境、未测场景或普遍效率提升 |
| 对照试验 | 相同输入与资源条件分别运行旧版和候选版，再独立评价 | 受控条件下两种策略的质量和成本差异 | 单例收益可直接推广到全部项目 |

结构检查只检查文件完整性、可解析性和已编码的约束，不运行 Agent，也不是以上三类中的行为通过证据。

## 运行与判定

1. 先声明本轮是场景推演、真实执行还是对照试验。需要测试独立冷启动时，每例在单独的干净会话加载待测规则，只提供该例 `input.md`；同一 Agent 批量读多例须明确记录，不能算多个隔离试验。
2. 被测 Agent 不读取 `expected.json`、其他样例和历史结论。
3. 保存输入、实际输出或动作产物的指针、规则版本、执行方式，以及实现者与评价者关系；同一版本重复执行时区分轮次。场景中的生产动作不授权真实执行。
4. 运行后由评测者逐条判断 `must_include` 与 `must_not`。命中任一禁止项即失败，缺失必要项须具体记录。
5. 结果保存在独立目录或已有验证记录中。未执行时只写“样例已准备”，不写“行为通过”。真实执行须记录哪些工具与环境实际可用、哪些步骤未做，不能把计划操作写成执行证据。
6. 对照试验记录相同的输入、模型设置、工具权限和验收标准；预期答案只供评价者使用。观察首次真实路径、总用时、可用的 token 统计、重复审查/验证、用户纠正、同根因返工与交付后缺陷。缺失数据记为缺失，不以字数、文件数或检查通过推断成本收益。

## 场景范围与历史证据

01–08 覆盖真实 UUID、假端到端验收、上传交互意图、虚构遗留数据、降级模式、同族修复、过时证据、普通任务与共享基础；09–14 覆盖轻量方案落盘、预期来源冲突、确认原型、执行证据、局部缺口恢复和最小交接。编号保留，便于追踪各场景。

本目录由原 `workflow-v2` 的通用场景迁入，现行输入变化不能追溯为历史通过。2026-09-15 的首批记录是**同一个独立 Agent 未读答案，批量读取八例后作出的场景推演**，不是八个彼此隔离的真实执行。见 [实际阅读记录](../../docs/features/20260915-workflow-v2/.goal/validation/blind-replay/_reading-log.md)。它支持当时批量上下文内的判断结果，尚不能证明单例冷启动表现、旧新流程差异或成本收益。

`execution/upload-preview/` 用于隔离控制器的实际修复与行为验证；其结果只覆盖该本地执行样例，不代替浏览器、真实项目或线上验收。后续新增执行证据保留本轮条件和原始结果，不改写上述历史口径。Goal v3 的专用独立核验场景见 [workflow-v3](../workflow-v3/README.md)。

15–20 覆盖当前运行现场、相关结果合批核验、时间/token 策略、共享资源操作、发布接任和提前预览边界。输入与判据已准备不代表行为通过；实际执行方式与结果另留证。

21–23 覆盖完整功能组前端先行与组间流水推进、后端领域职责及共享规则核验、有限技术探针与真实替换，以及成熟 API 小改不强制模拟的边界。

24 覆盖服务端开发态 Mock API 先准备、前端只调用已定协议、服务端暂时不能启动时不把筛选和读回写进页面，以及真实失败不回退模拟成功。该场景不追溯为旧推演通过。

25 覆盖本组前端体验门禁：默认画面相似、三句「已通过」、读源码或把真实保存叫做探针，都不能代替点完后页面变化的记录；浏览器打不开时本组停下。样例已准备，未运行 Agent，不能写成行为通过。

26 覆盖方案只有字段和错误码、没有使用场景时，先补方案，不把筛选、默认选中和保存后读回写进各前端。样例已准备，未运行 Agent，不能写成行为通过。

27 覆盖长任务下一动作逐段记录、加载或复用点名技能，并在自测和门禁允许后连续执行；用户明确限定单项时停在指定范围。不同阶段不合并为同一步。样例已更新，未运行 Agent，不能写成行为通过。

11/24 的实际执行夹具见 [prototype-http/request.md](execution/prototype-http/request.md)：独立执行者在临时副本修改页面与服务端，再由评价者运行 `verify.cjs`，检查动态原型、服务端候选变化、保存读回与失败反馈；任务 B 检查成熟接口的小样式修改是否被无谓扩张。Playwright 和 Chromium 复用环境已有依赖。执行命令与边界见夹具说明，实际轮次见 `results/`；不把脚本复跑写成新的 Agent 试验或旧新收益对照。

同一夹具的任务 C 仅补一次入口恢复：历史页面仍可打开、已有权威来源标明当前采用稿，接续者实际完成当前页面及 HTTP 路径；不以写入口说明作为通过条件。准备差异和独立结果追加在原验收目录，不覆盖 A/B 当时的规则快照。

28 覆盖已有大量操作/截图/CR通过时，仍须逐项对应采用稿；识别提前触发、按钮原文偏差、漏验分支不能被最终成功及P2标签吞掉。早期回放的结果和限制见[发布验证摘要](../../docs/releases/20261023-prototype-image-baseline.md)；不代表三端实际交付验证。

30 覆盖双向对照中的自行新增内容、业务新决定优先、比较条件不同不能直接判缺陷，以及工作流试验不能被扩成业务全流程或发布。独立文本回放只检验判断方式；不代表真实页面已按新规则修复。

32 从恢复实现和验收入口检查三阶段职责是否仍生效：找回有效已确认图片，不以实现截图重建参考，不用更新实现快照吞掉原型差异；合法需求变化留新采用版本并只使受影响证据过期。与31共同防止把图片准备后移给开发方。

28–32的实际回放范围、有限真实试验及证据限制集中见上述发布验证摘要；原始本机实验资料不作为这些通用场景的运行依赖。不要把32组文件结构通过写成32组行为通过。
