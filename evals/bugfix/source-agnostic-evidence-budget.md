# 评测：问题来源无关与证据预算

## 用户输入

我这里有一批问题，有些来自客服对话，有些来自截图和监控日志，还有几个 GitHub Issue。帮我结合代码判断哪些仍是问题，修复确认的问题，并给出验证证据。

## 期望行为

- 进入问题修复阶段，读取 `references/stages/bugfix.md` 和 `references/delivery/evidence-driven-delivery.md`。
- 不要求用户先把所有问题搬到某一个工单平台。
- 把不同来源归一化为来源、实际结果、期望结果、环境、角色、复现步骤和证据等级。
- 批量问题先展开父子关系，再按页面、角色、接口或共享根因聚类。
- 非问题、历史已修复和当前确认问题走不同处理路径。
- 界面问题使用运行态视觉证据；后端、并发和数据问题使用测试、接口或数据证据，不强制截图。
- 首轮代码审查前只做轻量界面检查；完成阻塞修复、准备复审前制作最终视觉证据，由复审同时确认修复和证据。
- 全量回归按实际影响无法隔离、项目要求或交付风险选择，不因 Goal/批量问题自动运行；证据与 CR 可在同一固定版本并行。
- 外部来源支持写回时才回写，并在写回后读回；不支持时在任务记录和最终回复中闭环。

## 禁止行为

- 把流程绑定到飞书、Jira、GitHub 或其他单一平台。
- 所有问题统一要求修改前后截图。
- 每条问题分别重复登录、启动服务和跑全量测试。
- 在首轮代码审查前反复跑全量回归。
- 单个低风险局部问题无条件跑整库全量回归。
- 界面自动化失败后无限更换坐标和参数。
- E2/E3 视觉问题因为截图失败就改用接口或数据证据并直接判定通过。
