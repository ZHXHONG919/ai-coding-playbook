# AI-Ready 接入检查

> 目标：在业务项目接入 AI-SDLC 或复杂 Agent 协作前，先清掉对 AI 不友好的基础问题。

## 使用时机

- 新业务项目首次接入 ai-coding-playbook。
- 团队准备把需求、方案、实现、测试、发布交给 AI 深度协作。
- 发现 agent 经常找不到入口、跑不起项目、漏测、误改高风险目录。

## 检查清单

| 维度 | Ready 标准 | 常见缺口 |
| --- | --- | --- |
| 项目入口 | `README.md`、`AGENTS.md` / `CLAUDE.md` 能说明项目目标、技术栈、启动和验证入口 | 只有口头说明或散落 wiki |
| 需求资料 | 需求、非目标、角色、验收标准有结构化 Markdown 或等价记录 | 需求只在聊天里，缺 Confirmed / Pending / Assumed |
| 架构事实 | 模块边界、关键数据流、外部依赖、发布边界可查 | 核心约束只在少数人脑子里 |
| 本地运行 | 安装、启动、测试、构建命令明确且可复现 | 服务起不来，缺 env 示例或 mock 模式 |
| 测试数据 | smoke 路径、测试账号/数据生成方式、安全边界明确 | 每次靠人工临场造数据 |
| 代码可读性 | 命名、目录、抽象、注释能让 agent 定位改动范围 | God module、废弃代码、隐式副作用太多 |
| 权限与风险 | 高风险目录、生产发布、凭据、外部写入动作有明确限制 | “不要乱动”只写在口头提醒里 |
| 可观测 | 日志、任务状态、失败恢复、发布健康检查有入口 | 失败只能靠猜 |

## 分级

- `Ready`：关键入口、运行、测试、风险边界都明确，可以进入 AI-SDLC。
- `Partially Ready`：可开展局部 AI 协作，但复杂方案、发布或跨端任务需要人工兜底。
- `Not Ready`：先补项目入口、运行验证和高风险边界，再谈多 Agent 编排。
