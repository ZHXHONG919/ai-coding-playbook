# 任务拆解：从采用方案到可执行功能

> 前置确定要交付什么，详细计划只展开到当前路径和近期依赖。Goal 统一使用 schema 3；字段见 `references/delivery/goal-v3.md`。

## 节点职责、输入与输出

任务拆解是技术方案与执行之间的正式承接节点：将已采用设计落实为具体工作、共同能力的负责位置、依赖和验证要求。它不重新设计业务，也不因文档齐全授予实现权限。已有确认、设计评审和实现授权直接复用，不增加一次审批。

```text
已确认需求 / UI Flow / 原型及固定图片
→ 技术方案及有效设计评审裁决
→ tasks/：共同领域能力 + 用例功能 + 实际工程依赖
→ 已授权直接执行，或 Goal Handoff 后连续执行
→ 按完整用户结果核验与交付
```

输入采用同一有效版本：完整方案第3章动作与结果、第4章领域职责和生命周期、第5章存储、第6章协议，以及相关质量与交接要求；轻量方案使用对应内容，不强制八章。UI Flow、原型和图片承接其采用依据，不因拆任务重新选择。缺少职责、结果或必要契约时回补方案负责位置；仅阻止真实依赖该缺口的工作。局部函数、文件和算法选择可在实现中补充。

复杂功能默认输出 `tasks/README.md` 和 `tasks/T01-功能名称.md` 至 `T0N`，一份文档讲透一个收敛功能或共同能力。模板见 [目录说明](../../templates/tasks/README.md)和[任务正文](../../templates/tasks/task.md)，写作深度见[贯穿案例](../../docs/examples/task-breakdown/README.md)。简单改动可沿用 `tasks.md` 或当前记录，只展开必要内容；已有任务包不为目录形式重建或改号。

## 按领域职责实现，按用例组织功能

从方案的共同规则和负责能力拆领域能力任务，从用例及原型拆功能任务。一个领域任务可以覆盖协作对象，不按每张表、对象或方法强制建任务；成熟能力直接引用。不是所有领域能力都属于高风险 `shared_foundation`，按实际规则变化判断。

- **领域能力任务**落实已定对象模型、属性与关系、生命周期、共同判断、内部接口及必要存储/事务。写明提供给哪些调用者、实际强制规则的位置；不能只罗列模型字段，也不要求概念与类或表一一对应。
- **用例功能任务**落实入口、上下文、操作顺序、调用编排、响应和界面反馈。明确调用哪项领域能力；不在控制器、页面、批量入口或恢复路径复制共同业务判断。
- HTTP协议承接方案，不等于领域内部接口；接口签名未定但近期必需时补回方案，不能在任务中各造一套。相似代码不自动提取通用框架。

编号用于稳定引用，不代表严格串行。一个功能文档内可有契约、服务端模拟、完整前端体验、真实能力接入和集成等工程步骤；依赖应落到步骤，不能以整个领域任务前置迫使全部真实后端先行，也不能让前端等待尚不需要的真实实现。交接前沿每个步骤的输入、产物和必要自测检查依赖是否可满足：模拟入口准备不要求尚未开始的页面先证明消费；检查放到产生该观测的步骤。共享基础若需真实消费者才能证明，将生产者、最小真实消费adapter及必要存储纳入同一基础的实现与核验，核验后才展开依赖该规则的其他消费者；不得以提前核验为由要求尚未允许实现的消费者先完成，也不以mock替代实际集成。保持既有前端体验门禁，不把全部后端称作探针。跨任务依赖引用 `T01 / S02` 等稳定步骤；共享规则在真实消费者依赖前核验，执行顺序仍以本页下文为准。

## 任务文档写到什么程度

每份文档按统一模板说明：目标与来源、负责/不负责的边界、具体功能行为、接口与能力协作、实施步骤及依赖、必要自测和缺口。关键行为以来源编号及必要原文就近摘录，完整枚举/协议精确引用，不复制整章；“实现注册”“按原型实现”只能作标题，不能作任务正文。执行者应能明确每个动作、条件、状态、失败反馈、请求时机和输出，无需重新拼多轮讨论。各小节不必独立建任务，不提前写死所有代码行。

全量已确认结果和功能行为先保留；近期任务展开到可执行，远期保留范围、来源、依赖和细化点。新规则先改需求/方案的负责位置，再同步受影响任务、Goal和证据；任务中的摘录是派生说明，不成为第二个业务决定来源。

### 界面任务必须定位采用原型和固定图片

在任务的“界面与交互依据”逐项定位本任务页面/弹层/区块和状态：采用版本及确认依据、可操作入口及到达步骤、UI Flow节点、固定图片的稳定路径、端/角色和比较条件。可以精确引用已有原型说明中的同一行，不另建图片台账；不能只引用整个目录或仅写文件名。共同入口可放目录说明，各任务仍须明确自己采用的状态及图片。已确认但定位信息未提供时，先查已有记录，不重新确认；确实缺失才回准备环节。仅在聊天无法访问材料时可交付标明待定位项的草稿，不能宣称达到近期可执行标准。

画面由已采用图片约束，交互由可操作原型/UI Flow约束，业务数据和请求由需求/方案契约约束，三者分别验证。图片覆盖哪些关键状态、哪些其他状态须操作验证应清楚；不要求每个状态都有图。按 `references/delivery/evidence-driven-delivery.md` 的三阶段规则，开发与恢复先实际打开固定图片，缺图、错图或版本不符回原型准备环节，不能由实现者自行截图并采用。任务明确保留项、已授权差异、界面基线及证据门禁；实际实现截图与参考图分开，不能覆盖基准消除差异。无界面任务说明无界面变化即可。

## 拆解完成标准与下游承接

拆解时先推导每步的可执行条件，再据此填任务与Goal；直接在任务现有步骤和验证表完成，不另建台账：

1. 从方案确定本步要产出的能力或可用体验，明确本步不承诺的后期结果。
2. 针对本步输出选判错样本，写清实际检查入口、要观察的事实及数据怎样准备，再确定所需前置。数据来源区分已存在历史、可执行的真实生产动作、受控合法初态夹具。查询/投影的局部检查可以用明确准备方式的终态初态夹具，只证明读取，不证明终态已由业务产生；审核、恢复、持久化等生产成立的结论必须走真实动作，不能预填结果自证。
3. 检查入口和样本生产能力都必须在本步或可完成的前置中可用。真实接收/查询尚无终态生产者时，本步只验已具备的接收、归属、初态投影；终态一致性移到真实生产者具备后的集成检查，或明确局部查询夹具的准备与证明边界。不能在self_check笼统引用包含未来状态生产的整项检查。
4. 将以上实现、观测和数据准备依赖共同形成执行顺序。若一条真实路径需要多个文档的接线，可用同一工程步骤明确引用这些文档及子步骤共同接回，再检查完整路径；也可先各自完成局部接线和局部自测，再由后续集成步骤验路径。不能让提交步骤先验完整结果页，而结果页真实切换却等该提交步骤done；不能在两个步骤都写同一切换工作却不明确首次接入和后续检查/清理各负责什么。

交接前把每项work/self_check回读到上述入口、样本准备、能力及负责步骤，不只检查depends_on图。服务/worker接线阶段可从其正常接口、调度入口及存储验证，真实页面端到端检查放到页面实际接回后；阶段局部自测不冒充完整路径，后期集成检查仍保留。核对失败时重排工作、合并必要接线或后移检查，而不是替任务声明通过。

交接前核对：全部已确认结果有任务覆盖；共同规则有唯一负责能力且相关入口均接入；近期工作、输入输出、依赖和判错样本可执行；界面采用稿、固定图片及操作状态可定位；设计缺口、负责人、解除条件和继续范围明确。复用有效design CR，不逐任务再审，也不要求所有远期细节先定稿。

`tasks/README.md` 维护覆盖关系与依赖，正文维护功能说明和工程步骤。未用Goal时在已有任务记录维护唯一进度；进入Goal后 `status.yaml` 是唯一进度，不再勾选文档维护同一状态。工程步骤自测完成不等于用户结果已验收。depends_on只表达工程依赖，仍须核实图片采用、完整前端体验及共享基础有效核验；不能以依赖步骤done代替这些继续条件。局部图片缺口还会间接阻止所属组体验放行及其后的常规真实后端，目录说明须列清该影响。

准备Goal映射前读取 `references/stages/goal-handoff.md`、`references/delivery/goal-v3.md` 和 `templates/goal-v3/goal.yaml`；`tasks` 是以工程任务ID为键的映射，保留owner等现有必需字段，不使用列表片段猜测schema。Goal沿用schema 3：`goal.yaml.tasks` 的工程步骤用稳定ID，通过现有 `work` 精确引用任务文件及步骤，通过 `results` 关联结果，`depends_on` 记录实际步骤依赖，`self_check` 引用文档检查项。文档可以是一对多工程任务；一个工程步骤也可以明确引用多个文档的协作步骤，保持接线负责范围与自测边界一致，不改schema、不新增强制字段。业务预期与原型采用依据仍进入结果的 `sources/decisions`。界面任务所采用的本地固定图片文件本身必须逐项进入相应结果的 `sources.path`，anchor对应具体UI状态；采用说明/原型HTML也保留。现行检查器只对直接列入的文件取摘要，不递归读取Markdown或HTML中的图片链接；只引用采用说明、任务正文或work，即使其中含图片路径，也不能让图片字节变化自动影响对应结果。按结果实际负责状态列图，不把整套无关图片加入全局inputs。恢复先读当前任务相关章节与来源、实际打开采用图片，不重读整个任务包；新建Goal、连续执行和核验分别由相应阶段负责。

## 先列全结果和共享基础

从已采用的方案及需求来源承接参与者结果、共同领域能力、存储与接口契约、关键成立前提和最早真实路径。完整方案的八章是说明设计的阅读结构，不是八组实现任务；交付按用户结果组织，服务端工作按领域能力及依赖展开。同一规则的多个入口共用其负责能力，不在任务中分别重新定义业务判断。

方案中的真实路径说明代表输入、入口、经过边界、最终消费者及仍模拟或未验证的能力；据此选择尽早证实关键判断的执行顺序。未定条件只限制依赖它的动作，明确处理点后继续其他工作；需要改变已采用设计时先回修相应来源及受影响契约，不在任务表默改前提。任务拆解承接方案设计审查的适用范围，不能把文档齐全视为真实能力已验证，也不因拆任务自动开始实现或强制创建 Goal。

结果清单是范围边界，不能因技术任务尚未展开而漏掉已确认要求。每个结果列出 `owner`、当前约定与来源、依赖，以及能否被真实操作或消费：

| 结果类型 | 如何划分 | 必须说明 |
| --- | --- | --- |
| `user_result` | 一条完整用户路径，不按页面、文件或 API 拆成多个验收结果 | 入口、对象、动作、保留上下文、去向/状态、关键反例；各动作或区块的当前来源 |
| `shared_foundation` | 本次改变、且后续工作依赖其正确性的高风险共享规则 | 规则与消费者、失败传播范围、提前核验入口；如身份、权限、计费、核心状态、并发或迁移切换 |

复用成熟 API、数据库或既有权限不自动增加基础结果。不要把每个技术任务换名为结果，也不额外创建只负责汇总报告的“最终功能”；最终覆盖是整个 Goal 的收尾条件。

先核实关键入口、上游类型、消费者与真实数据事实，再确定依赖。所有已知高风险基础和外部条件前置识别；普通实现细节随代码事实展开，不能把影响全局的未知推迟到最后。

## 近期任务怎样展开

选一个输入可用、能尽早证明用户价值的结果，由同一 owner 持续推进。只展开当前路径、近期依赖及解除高影响未知所需的探针；后续结果保留约定、依赖和风险，接近执行时再补工程步骤。

每项技术任务保留：**ID、关联结果、实际工作和输出、依赖、必要自测、状态**。一个改动影响多个结果时全部关联，不要求一个任务只归一处；不为任务单独创建验收批次、逐任务 CR 或 `accepted` 状态。

必要自测先写清：

```text
改变的行为 → 最可能的错误解释 → 能区分它的样本 → 真实入口/观测点 → 预期
```

例如“任务卡能进入成品”不足以判错；应使用不同任务和多个结果，确认入口保留当前任务。依赖已有测试前先看样本能否区分错误；build、源码字符串或复制实现常量的断言不能替代行为证据。按风险选择最便宜且有效的方法，不因任务存在就补单测或重复跑同一套检查。

展开、合并或删除技术步骤只改变实现计划，不改变已确认结果。发现新的结果或业务规则变化时，先更新当前约定和受影响范围，再同步近期工作，不重写整个工程任务表。

## 前端完整体验先行，按功能组接通真实能力

有确认原型、且需要新增或改变前端/API 交互时，默认以一个完整页面或连续使用过程为功能组。先明确本组包含的动作、状态与返回关系，以及与其他组的稳定边界；不按单个按钮拆组来跳过完整交互，也不把全部独立页面捆成一个组。复用现有结果与任务说明，不新增分组状态文件。

当前动作无法唯一定位本端采用状态、有效覆盖决定或正常运行入口时，由当前 owner 查明；缺失或过时且需要后续复用的信息补回已有任务说明、ui-flow 或运行说明。能从已有资料查明并正确执行就继续，不要求填齐固定清单、另写索引或逐页转抄。按原型还原的界面任务在开发前，按 `references/delivery/evidence-driven-delivery.md` 接收原型准备方已核对并采用的关键状态图片，将图片、可操作原型入口和业务约定一并交给实现者，引用同一采用稿位置；不只传目录，也不委托实现者自行截取基准。缺图或错图回原型准备环节处理，普通小改复用有效输入的边界不变。委派引用当前工作真正需要的来源与运行说明，不能仅传目录或要求“读完全部文档”。链接可打开不代表采用版本、目标端和实际运行系统正确；确认与证据复用沿用现有规则。缺口只限制依赖它的动作，不新增审批或通过表。

```text
CONTRACT → FE_MOCK_LOOP → SERVER_CAPABILITY → MOCK_REPLACEMENT → INTEGRATION / QA
契约       本组完整前端体验   按领域能力实现       逐步替换接口模拟      真实功能验收
```

| 步骤 | 输入与工作 | 产物及继续条件 |
| --- | --- | --- |
| 契约与模拟接口准备 | 当前原型、需求、领域职责，以及方案中的使用场景 | 使用场景写清：哪次操作调用哪条入口，成功和失败时页面看到什么，筛选、默认选中、保存后读回由服务端哪条响应决定。只有字段表不算完成，先补进方案，不在页面里现编。然后按方案在服务端用模拟数据做这些入口。前端只取数、提交、展示错误 |
| 前端模拟 | 原型阶段已确认的图片版本、可操作采用稿、已明确的契约与可调用的服务端 Mock API | 打开图片按图实现，正式页面通过正常请求层发送真实 HTTP 请求，由服务端返回模拟响应；本组约定的浏览、编辑、保存、取消、返回及相关加载/空态/失败/权限/冲突状态可操作，并保持对象上下文 |
| 前端体验检查 | 同版参考图片、运行中的本组页面及其实际截图、可操作采用稿，以及点开后才出现的状态 | 同视口逐图比较并操作这些状态；实现截图不能替换基准。现有记录写下每个动作点完后页面变了什么，以及哪条请求是这次点击引起的。没有这些差异，不得进入真实后端，也不得把布局用到其他页。三句「已通过」、实现者事先列的名单、子代理的「已对照」、读源码或请用户逐页找差，都不算通过 |
| 服务端与模拟替换 | 领域设计、接口契约及已可操作的前端 | 按领域能力及依赖实现；每个能力具备后接回前端，尽早完成第一条真实路径，不等本组全部后端写完才联调 |
| 真实验收 | 已替换模拟的完整操作及仍有效的证据 | 验证真实权限、持久化、副作用及最终消费者；相关使用过程按审查规则合批核验 |

完整前端体验以本组已确认范围为准，只覆盖相关状态，不穷举所有组合、不扩张视觉打磨。组 A 按 `references/stages/review.md` 完成采用稿与操作证据的覆盖核对后，才可实现 A 的服务端；独立组 B 可以继续前端工作。并行仍须满足输入和资源边界。首个代表页面先校准当前这一态，不能据此把布局用到其他页，也不代表本组其余交互已完成。前端模拟通过只证明体验与接口消费方式，不证明真实业务能力。

默认由本组 owner 安排接口实现者在项目现有服务端提供开发态模拟 API，前端调用约定路由，不默认使用浏览器请求拦截或组件内假数据。一个 Agent 可以同时承担接口准备和前端实现，不为 Mock 固定增派角色或独立服务。用户或项目明确采用其他机制时遵从并记录依据。服务端暂时不能启动时，只做不依赖这些数据的版面，并保留接口缺口。筛选、默认选中、保存后读回仍等服务端模拟入口，不能写进各前端，也不能把本组标成通过。

模拟接口准备属于前端先行的前置工作：复用项目路由、参数类型、响应和错误约定，在接口后的数据/业务实现处提供可替换的模拟响应。覆盖必要状态切换和失败样本即可，不另造完整规则引擎；模拟数据与写入限于隔离的开发夹具，不产生真实业务副作用。用页面网络请求及服务端请求记录或等价观测核实调用到达，HTTP 成功只证明传输与响应，不能证明真实权限或业务能力。

模拟启用范围、真实替换负责人、替换点及清理条件写在已有记录中；负责人沿用本组 owner，明确接回后才能转交。随后保持约定的 API 路由、请求/响应和错误语义，逐项替换服务端内部实现，前端正常调用方式不变。开发态显式启用模拟，生产入口不得启用成功替身；真实逻辑失败不得回退到模拟成功。确需修改契约时同步模拟、前端消费者与真实实现，并复查受影响体验，不为迎合模拟数据改变领域事实。

### 何时调整顺序

- 已有真实能力可用时直接复用；成熟接口的局部改动、纯后端或无新交互的工作，不强制重做页面或引入模拟。尚无明确界面依据时先按方案规则补齐本次需要的依据。
- 影响可行性的外部能力、性能或新共享语义，允许在前端完成前做有限真实探针或必要基础核验。在已有计划写清要回答的问题、最小范围、停止条件和影响；不能借“尽早真实路径”提前展开全部常规后端。本组尚未记下点完后的差异时，该组的真实保存、删除和持久化不叫探针。失败只阻止依赖该结论的工作。
- 模拟消费者只依赖已明确并核验的协议语义；尚未成立的权限、归属和状态规则不能靠假响应固化。真实共享基础仍按下一节在实际依赖前核验，探针通过不代替完整能力或最终验收。
- 用户或项目有明确实施顺序时遵从，并说明实际验证边界；不把默认顺序再变成一次审批。

路径写具体输入、应用入口、实际经过的边界、最终消费者及未经过的外部能力。例如“保存配置 → 预览读取 → 实际任务解析 → provider 请求含新值”，不能写成“接口 200”。目标环境、必要代表数据和工具能力尽早核实；付费/生产动作依已有授权执行，未执行保留缺口。

## 共享基础与隔离依赖

共享基础必须在消费者依赖其新规则前完成正式验证和 CR；内部相互依赖的实现步骤可作为同一基础中的技术任务，不为每一步再建基础。

消费者需要的是稳定协议还是已验证真实能力，要明确区分：

- 协议能独立确定时，限定输入输出、错误、状态和副作用。必要的协议核验通过后，可供消费者开发或模拟联调使用；真实集成仍依赖真实能力。
- 未解决的权限、数据归属、状态等语义不能用接口签名代替。不能把协议通过写成整个基础通过，也不能复用旧结果编号去证明一个被缩小的断言。
- 缺失能力在原结果下保留待完成工作、owner、解除条件、回收点及真实检查。生产代码不得返回伪造业务成功；TODO 和 mock 记录本身不算证据。
- 基础约定或实现改变时，沿生产者、全部消费者及恢复入口标出受影响结果；依赖旧基础的证据不再证明新基础下的行为。无关结果及证据保留。

具体隔离和阻塞处理见 `references/delivery/agent-delivery-flow.md`。

## owner 与并行边界

默认当前目录和现有环境，不主动创建或切换 worktree。结果清单用于防漏，核验分组按 `references/stages/review.md` 的连续使用过程决定，不按结果编号一一安排 CR。

同一 owner 贯穿准备、实现、集成和返修；需要换人时交接当前结果、采用依据、代码版本、缺口和写入范围。工程分工服从用户路径：要求同页弹层，就协调详情页与组件的写入，不能为分开目录改成独立页面。

共享契约、migration/Entity、核心状态或公共服务由一个 owner 收口；进程、端口、数据库、队列和运行配置的操作同样明确归属，不能只检查文件冲突。独立区块、已稳定契约的 adapter 等可并行，明确写入范围和整合责任。需要更新正在使用的约定时先同步受影响 worker；失联写入者未确认停止前不能接管其范围。正式核验使用固定版本，独立工作可继续。

## 记录、工具与完成标准

技术任务仅用 `todo → in_progress → done`；`done` 表示本步骤完成且必要自测通过，不表示用户结果通过。失败或阻塞保持未完成，并说明原因及可继续范围。

结果通过由正式检查证据判断。schema 3 在运行记录保存版本差异、改动到结果的映射、结果检查及独立 CR；当前有效性由工具结合历史记录推导，不手填一套结果通过状态。检查不能替代未完成的本次必需技术工作。收尾核对全部结果与最终增量，不因全部任务 `done` 或 CR 没有 finding 宣布完成。

证据等级、界面基线与证据门禁按结果和风险选择，方法见 `references/delivery/evidence-driven-delivery.md`。同一路径、角色和状态共享有效证据，不按技术任务重复截图。第三方工具按 `references/delivery/tooling-prerequisites.md` 共用一份能力/安装/认证清单；引用已有清单位置，不给每个任务重复安装、登录或建清单。
