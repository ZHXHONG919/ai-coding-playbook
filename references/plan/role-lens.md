# 方案规则：角色视角与决策责任

Priority: CRITICAL

## 规则定位

角色不是一句“你是资深架构师”的提示词装饰，而是一组必须履行的观察视角、决策责任和输出门禁。

使用本规则时，先判断当前阶段需要哪些角色视角；输出可以不逐项展开角色名，但结论必须体现这些视角已经被使用。

## 总原则

- 角色视角用于补齐盲区，不用于堆砌头衔。
- 每个角色必须回答“我负责发现什么问题，阻止什么错误，做出什么取舍”。
- 没有证据的判断只能标为推断或待确认。
- 多角色冲突时，必须给出取舍理由，例如业务效率、数据安全、交付成本、长期维护性之间如何权衡。
- 普通小改可以轻量使用；复杂方案、DB、权限、异步、LLM、发布链路必须显式体现关键角色判断。

## 阶段角色视角

| 阶段 | 必须视角 | 核心责任 |
| --- | --- | --- |
| 需求理解 | 业务负责人、产品负责人、领域建模者 | 识别真实业务问题、使用场景、边界、非目标、验收口径 |
| 技术方案 | 业务架构师、技术架构师、交付负责人、资深 Reviewer | 抽象稳定概念、定义系统边界、设计工程映射、预判风险和反例 |
| 实现落地 | Senior Engineer、代码维护者、测试负责人 | 小步实现、复用现有模式、控制变更范围、保证可验证 |
| Review | Staff Reviewer、专项 Reviewer、发布风险负责人 | 找出 P0/P1 风险、契约破坏、数据/安全/并发/测试缺口 |
| Bugfix / 排障 | Incident Commander、Debug Owner、回归验证负责人 | 复现、定位、验证假设、最小修复、防止引入无关改动 |
| 发布检查 | Release Manager、SRE、数据负责人、业务 Owner | 确认发布窗口、迁移安全、回滚路径、观测和业务可接受风险 |

## 角色责任细则

### 业务负责人 / 产品负责人

- 明确用户是谁、触发入口是什么、成功后业务状态如何变化。
- 区分必须做、暂不做、不能做。
- 给出验收口径，而不是只描述功能列表。
- 识别流程里人工审核、运营动作、异常兜底和责任归属。

### 领域建模者 / 业务架构师

- 先定义核心概念，再讨论表、接口和页面。
- 区分对象自身、对象关系、任务上下文、计算结果和外部产物。
- 说明概念如何创建、修改、审核、失效、重算。
- 识别长期稳定规则，避免被一次性流程污染领域模型。

### 技术架构师

- 说明模块边界、依赖方向、数据流和状态流。
- 给出关键设计取舍：为什么这样拆，为什么不选替代方案。
- 识别兼容性、扩展性、幂等、并发、事务、性能和可观测性风险。
- 对外部 provider、LLM、异步任务、文件/媒体产物给出失败恢复路径。

### 交付负责人

- 把方案拆成可独立验证的任务。
- 明确上线顺序、灰度/开关、回滚、数据补偿和 smoke。
- 区分本轮必须交付和后续优化。
- 识别哪些问题会阻塞实现，哪些可以带风险推进。

### Senior Engineer / 代码维护者

- 复用项目已有抽象和命名，不为单次需求创造孤立体系。
- 控制改动半径，避免顺手重构。
- 确保 DTO、Entity、API、前端 Model、Job 状态一致。
- 为未来维护者保留清晰边界和必要注释。

### Staff Reviewer / 专项 Reviewer

- 优先找正确性、安全、数据破坏、权限绕过、契约破坏和发布阻断问题。
- 对 DB、权限、前端、异步、provider、发布脚本分别按专项风险审查。
- 不把个人风格偏好写成必须修改。
- 没有发现问题时，也要说明剩余验证缺口。

### Incident Commander / Debug Owner

- 先复现或收集足够证据，再进入修复。
- 每次只验证一个主要假设，避免多处同时修改导致无法归因。
- 判断影响范围、用户影响、是否需要止血或回滚。
- 修复后补充回归验证和监控观察点。

### Release Manager / SRE / 数据负责人

- 确认发布目标、窗口、分支、环境变量、migration、任务开关。
- 明确健康检查、日志、指标、告警和人工观察点。
- 数据变更必须有可重放、可回滚或可补偿方案。
- 不可逆操作必须标红，并给出人工确认点。

## 输出门禁

复杂技术方案至少体现：

- 业务视角判断：业务目标、非目标、验收、人工流程。
- 领域视角判断：核心概念、职责边界、生命周期、稳定规则。
- 架构视角判断：模块边界、数据流、状态流、接口契约、替代方案取舍。
- 交付视角判断：任务拆解、上线顺序、测试验收、发布/回滚风险。
- Review 视角判断：反例、边界、失败路径、P0/P1 风险。

复杂 Review 至少体现：

- 正确性和契约风险。
- 数据、安全、权限、并发、幂等风险。
- 发布和回滚风险。
- 测试缺口和无法验证项。

排障和发布阶段至少体现：

- 当前证据和未知项。
- 影响范围和优先级。
- 最小动作方案。
- 验证、观察和回退方式。
