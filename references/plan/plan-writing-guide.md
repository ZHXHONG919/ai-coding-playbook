> 版本：2026-10-22 · 内容基线：v43

## 使用范围与设计主线

技术方案是后续任务拆解、实现与验收的共同依据。它把已确认需求转成可执行的领域职责、数据和接口契约，使实现者能完成集成并验证用户结果；近期必需设计应明确，后续局部细节有补齐点。

本规范用于完整技术方案。普通字段、样式和成熟接口的小改沿用轻量入口；完整方案中的无变化章节引用已有设计即可。正式产物为 plan.md 与必要图源、图片，需求引用采用版本，任务和执行状态另见 tasks.md / Goal，不要求增加 HTML 阅读文件。

设计从同一个业务问题逐步展开：

```text
需求与项目事实 → 参与者资格、入口及受影响行为
→ 动作结果边界与查询的业务含义
→ 共同职责及所属概念、属性、具名关系的完整定义
→ 存储与协议共同落实；图采用同一定义
→ 代表与边界实例验证；观测、质量及实施交接
```

领域能力指负责一组业务行为和共同规则的能力，例如“内容审核”。用例分析说明参与者怎样完成目标；同时从本次影响的对象和事实，找出会改变这些事实的既有行为。两者共同决定由谁负责规则、哪些信息属于谁，表、接口和任务再承接结论。只追查与本次规则有关的状态、字段、入口和消费者，不扩成全系统盘点，也不把相关旧行为变成本次新增需求。

八章是阅读顺序，也是定义的负责位置。先从用例确定动作条件、结果边界及读取含义，再归纳共同职责，完整定义实际依赖的属性和具名关系；存储、API和图采用这些结论，不各自从摘要重新生成含义。少量实例用于发现差异、检验连续操作，不能用实例中恰好出现的状态、值或连线限定定义范围。定义与实例分别成立才可交付。内容直接写入所属章节，完整已有定义可精确引用，不另交台账、中间文档或思考记录。

业务资格不等于某个既有页面或接口的权限，服务名相同也不证明所有写入使用同一判断；这些关系要在工程映射前说明。协议发现缺少可执行动作时回查职责，持久化无法保证结果时回查模型和协作。系统概览在结论稳定后回写，质量约束从开工起参与判断。

需求和已核实的项目事实约束设计。先把本次涉及的业务约定解释成动作条件、所需信息和完成后必须保留的事实，再在此范围内提出技术推荐。关键选择说明依据和成立条件；未决选择先找出会改变哪些动作及结果，相同部分继续形成完整设计，会改变的部分保留明确条件，不能按章节整片延期，也不能把尚未决定的选择变成既定事实。

各章按“输入—分析—输出—检查”组织编写工作，正文呈现可审查的结论及上述依据，不复制思考记录，也不为每个字段建立来源表。工程字段、模块及技术参数可以给出有理由的建议，无需逐项请用户决定；改变业务规则则回需求来源。方案的完整性包括清楚交代未决边界，不靠虚构条件补齐。已有概念和能力先核实，不因名词、接口或页面增加，就默认新增对象、表和服务。

篇幅随实际变化决定，尤其第7、8章：已有能力足够时，一句说明沿用依据及本次影响；有局部缺口只补相关项；新高影响路径才专项展开。没有新增监控或质量目标，仍要验证本次行为及原有权限，不补空表、不编目标值。

## 八模块的输入、推导、输出与相互校验

### 1. 背景与目标：明确设计所处的系统

**输入：** 需求采用版本、允许参与者完成目标的业务条件、真实入口和消费者、受影响对象的现有职责与生命周期、已确认交互稿，以及相关质量约束。

**分析动作：** 说明业务问题需要哪些技术变化，先界定参与者和对象所处的实际系统。参与者从哪里取得必要信息、选择对象和执行动作？本次改变哪些业务事实，现有谁还会读取或修改它们？按 `references/plan/evidence-first.md` 从这些设计判断查找相应定义及使用位置，核实相关页面、API、内部能力及调用者的实际约定，将已取得事实带入后续设计；缺口只限制证据实际不能支持的结论。形成有限的受影响范围。跨产品时沿“入口产品 → 共享能力 → 后续处理”确认归属。业务资格、系统角色、接口权限分别取证，不能从名称或页面原型互相推出；源码证明现状，也不能自行替代新需求。

以项目已有架构和需求划定技术选择范围，优先复用已有组件。项目未使用、需求未明确要求引入的新基础设施不列为备选；现有能力不足时先给验证证据及约束缺口，回到需求或技术目标确认。高影响未知在依赖前核实，可隔离问题记录最晚确认点，其他工作继续。

**输出及使用者：** 技术目标、参与者与受影响对象的上下文、相关入口和证据边界，供第2—4章共同使用。已核实事实、本方案推荐和缺失调用点分清，未知说明需要什么证据、影响哪个依赖。涉及结构变化时给系统概览，标清沿用、修改和新增；未变部分引用已有图。业务目标、规则、范围与验收引用需求，不再维护副本。

**检查与回溯：** 每项变化有需求或用例依据，责任归属有项目证据。后续发现边界遗漏时回修概览；需要改变业务语义时回需求来源，不能以技术方案默默追加门槛。

**批量审核贯穿例：** 教学前提是已有管理端、单体内容审核能力和 PostgreSQL。需求明确异步逐条处理和结果找回，因此后续分析持续执行和查询职责；执行方式在已有应用与数据库内设计，不加入未要求的消息队列比较。

### 2. 用例总览：确定参与者要获得的结果

**输入：** 目标、系统边界、参与者、需求规则，以及第1章核实的入口和交互基线。

**分析动作：** 从参与者目标识别系统用例，区分目标、操作步骤和内部机制。多个终端可共用用例及规则，保留实际入口差异；不按按钮、表或 API 复制用例。与本次规则有关的既有用例引用其来源或标为沿用，供后续职责分析，不重新包装为新增交付。系统外的自动系统也可成为参与者。

**输出及使用者：** 用例图、稳定编号、参与者、成功结果和需求依据，供第3章展开行为，并为后续验收确定对象。

**检查与回溯：** 用例能说明谁得到什么结果，粒度相近、需求有承接。相似行为先进入职责分析，不立即复制服务；说不清结果时回查目标和边界。

**批量审核贯穿例：** UC-01“批量通过内容”、UC-02“查看处理结果”表达审核人员的目标。领取任务和写数据库是内部步骤，执行进程不画成业务参与者。

### 3. 用例分析：从行为发现共同职责

**输入：** 用例、需求规则、参与者业务资格与实际入口条件、受影响对象的既有行为、采用的交互稿及质量约束。

**分析动作：** 先从采用的业务规则和公共身份约定构造参与者、对象范围及状态，不预先赋予旧入口额外要求的资格。沿必要读取、选择和动作，将每个旧入口条件与业务起点比较；若入口另要求来源未要求的条件，就选满足全部业务前提却缺少该额外条件的身份作设计样本，不能靠角色名称假定它必有。样本不违反已核实约定；有来源证明业务资格必然包含该条件时，可直接采用，不制造不可能组合。只覆盖本次存在差异的依赖，不穷举权限。

先确定本动作面对哪些当前事实、哪些条件允许执行，以及各相关情形的成功、合法无变化或拒绝结果。范围来自本次动作涉及的合法状态、关系和存在/缺失情况；结果相同可合并，不做全系统组合穷举。已确认结果直接采用；不改变业务语义的响应由方案给出有理由的候选契约，真正未决的业务差异才局部保留条件。界面不提供入口或状态图未连线，不能代替服务端对该情形的结果定义。

下面的用例分析表或等价短说明承载动作定义。逐步比较业务前提与真实入口的条件，确定完整采用、部分复用并受限接入或真实冲突；读取、选择和执行各按自己的依赖判断。从参与者需显示、选择、筛选和回看什么结果反推必要读取，说明各结果集合的范围、筛选和业务顺序，供第5、6章落实；不只追踪执行动作前的主列表。定义所需信息来自用户、上游响应还是上下文，并将成功及拒绝结果传给协议。部分复用只在业务已允许的对象及信息范围接入，保留旧授权和消费者，不预定新增服务或换高权限身份代调用。

| 业务动作、已确认前提及依据 | 必经能力及现有调用条件 | 采用方式、当次必需信息及来源 | 完成事实与失败边界 |
| --- | --- | --- | --- |
| 来源允许谁对什么对象做什么 | 本步实际入口/内部能力；身份、权限及对象范围，缺实现则注明已知边界 | 条件相容才整体采用；否则给受限接入与兼容，说明用户输入、响应或上下文怎样提供信息 | 同一参与者能完成的结果，以及必须拒绝的条件 |

据此识别每一步需要的知识、状态和职责，并说明结果成立时哪些事实必须保持一致。再从这些事实找回相关既有操作，判断它们与本次行为如何相互影响；已知行为引用事实，缺失调用点只标明影响范围，不虚构入口或替未知业务规则拍板。交互边界、流程协调和业务规则可辅助分析，不要求各建一层类。外部核验及恢复以真实契约为依据，不能用设想补全能力。

表中就近引用规则编号及必要原文，直接形成可使用的条件与结果。先按消费者完成目标所需的读取、选择、动作及结果后读安排路径，再取满足相关领域与生命周期约束的少量起点；可合成合法数据，不要求重演完整创建史。人工注错另说明前提与用途，不将损坏状态当作正常行为形成的事实。详细实例按第6章生成，不代替未走到情形的定义。涉及并发、重复或恢复承诺时，交错两个执行者的读取、等待、取得保护、判定及结果保存，核实等待后事实及保护位置；不能只列锁或唯一键就视为承诺成立。

推演失败分支和待定选择时，把候选结果代回同一动作的已确认条件：是哪个条件确实不成立，还是已确认前提仍成立却被新守卫拒绝？后者改变了业务结果，需要回需求，不能作为技术保护默认加入。先以动作资格、信息义务和成功结果筛选兼容答案，再比较它们真正改变哪些动作、事实或关联。未知若只影响动作是否适用，就限定在前提事实的判定；前提仍满足时，既定结果继续成立。真实项目事实若证明约定无法同时满足，明确冲突及直接依赖，回需求决定，不自行缩减行为。各兼容答案下都相同的约定与验证结果继续展开，真正变化的部分给条件设计或最晚决定点；若涉及核心身份、结果单位或关联数量，相应模型和键也保持未定。这些依赖随第4—6章传递，不留到文末才写一句“待确认”。

**输出及使用者：** 动作条件、必需信息、完整结果边界、读取的业务含义、接入结论和局部未决范围，以及检验它们的代表场景。第4章由此归纳共同模型，第5、6章落实保存与调用，不能用选中实例缩小定义。第7、8章采用既定结果及实例补观测和质量验证。

**检查与回溯：** 关键动作有责任承接，所需身份与状态前提能由此前合法行为建立；失败后的修改及人工处理也按同一方式检查。缺少规则回需求，缺少负责能力回职责分析，不能靠再加页面或 API 掩盖。

**接入推导例：** 来源允许资格A的登录用户在指定对象范围完成动作，之前须读取候选项；旧读取另要求B，身份约定未规定A必含B。用满足A但没有B的甲走读：甲仍应完成动作，旧入口则继续按B拒绝，因此只可复用真正相同部分，并在A已允许的对象及必要信息范围内设计接入。后续协议继续使用甲，不改给甲增加B；有来源证明A必含B则可完整采用，真实能力冲突只限制对应依赖。这是设计样本，不声称存在相应真实账号。

**批量审核贯穿例：** 响应丢失导出提交身份和归属职责；每项成功对应实际审核，失败需说明原因，终态需记录时间。等待中尚无终态事实，不表示到达终态可以省略；先确定行为义务，再选择状态、字段和表。

### 4. 领域对象设计：形成多个用例共同使用的模型

**输入：** 已推演的动作条件、所需信息及完成事实，相关既有生命周期与读写行为，以及各未决选择的实际依赖范围；同时带入已有能力的真实边界。

**分析动作：** 先归纳共同能力及其负责的规则，再确定这些能力管理哪些概念、概念之间怎样协作。沿以下顺序形成同一份模型：

1. **检验规则的适用范围，再确定负责能力。** 先保留各动作的条件和事实成立时点，找出会改变这些事实的相关既有操作，判断关系经过这些合法变化后是否仍须保持；对会影响它的未决答案分别推演。需求明确要求长期成立，或有依据证明适用于相关变化的关系，才归纳为相应范围的共同规则。依据不足时，保留为动作前提、事务完成后的事实或条件性规则，再确定负责能力；单次动作完成的状态不能自动代表对象整个生命周期。业务规则是否适用与现有实现是否已保障分别判断：已明确的长期规则继续作为基线，缺少写入者证据时核实接入，不重开业务决定。应用服务协调操作，稳定判断归所属能力；不能只保证新入口之间一致，也不复制判断或把全系统塞进一个服务。
2. **辨别概念的性质。** 描述主体且随主体管理的信息，可以是属性或一组有整体含义的值；需要持续识别、独立变化和管理规则的概念，才考虑独立对象。再区分关系、一次任务上下文及计算结果。业务编码的唯一性范围由规则决定，有编码不自动意味着独立实体或表。
3. **分别推导关系两端的最小与最大数量，再生成图。** 先明确具名关系的端点是整个类型还是有条件的子集。最小数量由合法创建、解除及保留行为决定，最大数量由业务规则及真实约束共同决定，不能由“一对一”等简称同时补出两端下限。必填引用只约束持有者，唯一约束只限制最多；例如A持有非空且唯一的B标识，已有存在性保障时可说明每个A有一个B、每个B最多有一个A，不能据此证明所有B都已有A。反向至少一个需要单独的业务或生命周期依据。上例可画为 `A "0..1" --> "1" B`：标在A旁的数量表示每个B对应的A个数。各角色关系形成“一个合法A能关联多少B、一个合法B能关联多少A”及何时为零的定义，再用未参与及变化后保留对象检验。图只翻译这一定义；ER映射完整物理表时保留其他合法记录，未决范围保持条件。
4. **先定义属性在合法行为中的含义，再选择工程表示。** 对直接读取/比较、写入或消费的属性，找到所属概念或契约，确定业务类型、允许范围、产生条件、初值与null。属性会被相关动作改变时，从合法起点和动作的边界结果推导它需要承载的值或结构；一次输入与累计、转换后的结果分别判断，再选择能保存和传递这些结果的类型。当前列或接口类型是现状证据，不自动成为新行为的业务上限。已知合法结果与现有表示不相容时，第5、6章形成兼容的候选表示及消费者调整；真正未知只保留在不能推出的范围或集成条件。边界样本用于检验，不能把样本最大值当成新业务上限，也不默认扩大全部字段。

   新属性由相关用例归纳，旧属性采用真实定义并与上述行为核对。枚举取值给完整机器值及逐值中文，数值范围说明边界和精度。只比较一个值不缩小所属值域，字段未改也不免除本次依赖；引用缺少中文等内容就在本处补齐。跨边界关键字段明确生产者/消费者及当前值或快照。已有同等完整定义可引用，节选注明范围，不补造未知全集；仅消费业务判断能力时不追无关内部属性。
5. **完成协作与工程映射，再回看选择的影响。** 将共同能力及第3章接入结论映射到实际入口和强制位置，说明调用者、允许读写的事实及一致完成的变化。受限接入说明服务端怎样取得对象范围、调用内部能力及维持旧契约；原接口不允许当前参与者调用时，不能换个路由名仍原样调用，也不假定内部签名已提供这种能力。采用模型、表示或协作方式后，沿变化的事实反查已有生产者、入口、协议及消费者，确定实际受影响的契约。第5、6章共同给出有理由的候选接续方式、过渡期间可见行为及启用/退出条件；已知旧契约与新选择的冲突由方案处理，真实调用点或部署设施未知只限制具体接入核实。已有保障足够就引用，需调整给职责和兼容安排；这些结论供存储与协议承接。同一服务名或条件更新签名不是保证，概念不与类、表或服务一一对应，技术任务不自动成为核心实体。

在协作和变化点明确后判断设计模式：当前困难是什么，简单实现是否足够，采用模式能减少什么复杂度，又增加什么成本。实际有可替换算法才考虑策略模式，状态行为确实分散复杂才考虑状态模式；不为未来可能出现的动作预建框架，也不因有状态机就逐状态建类。只解释实际重要的选择。

**输出及使用者：** 共同能力、概念性质、完整属性定义、每条关系的双向数量与变化规则、工程承接及取舍。图据此生成，存储/API仅映射表示法，不重选含义。存在关键多状态或重试/恢复生命周期时给状态机及转换条件；不因普通关系变化或命令结果另造生命周期。第5、6章共同落实，第1章回写系统概览。

**检查与回溯：** 同一模型能解释多个相关用例及关键异常；规则有统一负责能力，当前事实和历史结果不混淆。若新增功能总要复制判断、到处拼关系或新增转发层，回查概念和职责；不能把“图中有对象”视为建模已经完成。

**批量审核贯穿例：** 内容审核能力负责合法状态变化及审核记录；批次处理能力负责一次提交及结果组织。提交人和请求标识是批次属性，批次项承载本次逐条结果，租约属于执行上下文，汇总属于计算结果。多个入口共用审核能力，不能为批量或恢复复制审核判断。

### 5. 库表结构设计：选择这些事实的保存方式

**输入：** 第4章的概念、共同规则及负责边界、相关读写入口与未定条件，用例查询、历史及保留需要，以及既有存储和数据量。

**分析动作：** 将第4章同一对象范围和关系映射到字段、查询及约束，先核实已有结构能否承载已确定的属性及合法变更结果。ER采用实际表中所有相关合法记录的数量，不把模型子集冒充共享表；区分当前引用、历史归属和目标可查询性。每项保存事实确定实际列，结构化值定内部键、层级、类型与空值；供API消费时与第6章共同形成具体类型/映射。枚举连同中文采用所属定义，编码不同才列映射；应用初值与DB默认分别决定，列可空不免除动作必需输入。按第3章交错场景安排事务、读写及保护顺序，说明执行者等待后怎样继续判定、在哪一步足以保证承诺，再交给接口与恢复流程采用；不能用机制名称替代过程。表数不由对象数决定，未决仅限制实际受影响结构。

| 保存方式 | 适用依据 | 需要说明的代价 |
| --- | --- | --- |
| 复用已有列或关联 | 含义、归属、生命周期与现有事实一致 | 现有写入者及兼容影响 |
| 所属记录中的结构化值，如有界 JSON | 同一归属、整体更新、规模有界，没有独立访问或约束需求 | 结构版本、校验和查询限制；不能藏入无界历史或独立并发子项 |
| 独立表与逻辑关联 | 确有独立更新、访问、身份或一致性需要，既有结构不能合理承载 | 联查、事务、索引、清理及维护成本 |
| 不重复保存 | 可从可靠事实计算或只需即时展示 | 计算成本及历史结果是否需要冻结 |

例如，同一主体下随资料整体修改的有限附件及说明，可以保存为有明确结构的值；有独立并发处理和恢复要求的条目则另作判断。复用“日志表”前核实它是可靠业务记录还是运行日志，检查完整性、写入方式、保留期和查询能力。不能仅凭名称复用，也不为每个流程步骤另建记录表。

表间禁止数据库外键（FK）及数据库级联，包括 ORM 自动生成的外键。类型一致的关联 ID 表达逻辑关系，由负责业务能力按用例规定的时点维护存在性、归属、失效和清理；允许逐条失败的情况不能改成提交时整批拒绝。同生共灭的变化由应用事务控制，历史 ID 保留规则明确说明。关联索引依据真实查询和清理路径设计，已有联合键前缀足够则不重复建索引；主键、唯一键和检查约束仍按规则使用。

**输出及使用者：** 表和字段、类型、可空和初值、唯一及检查约束、逻辑关系与索引、事务并发、保留与迁移回退。枚举字段同时说明实际存储值及中文含义，区分应用写入初值与数据库默认值；即使用 varchar 或整数存储，也要给允许值。与第4章定义相同可明确引用，编码不同则列对应关系，并与API取值核对。ER 展示物理表名、字段及中文含义，详细格式见下文表达标准。第6章核对协议承诺，第7章定位观测，第8章验证容量和恢复。

**检查与回溯：** 每项持久事实有用途，新增表和关系有不能合理复用或合并的依据；数据足以保证场景，但不迫使调用方分散维护规则。存储不能把未定业务选择固化为无条件约束或清理政策；正常过程记录等不依赖该选择的设计仍可继续。无法满足用例时先回查模型和执行方式，不默认增加表、字段或映射层。

**批量审核贯穿例：** 批次保存提交身份，条目独立领取和更新，因此分表；既有审核记录复用。去重信息留在批次，执行信息留在条目，汇总计算，不另建映射或统计表。应用维护关联及清理，内容、审核记录和成功结果同事务提交。

### 6. 交互 API 协议：让调用方实际完成用例

**输入：** 已推演的参与者路径、领域操作与共同规则、复用能力的调用条件、消费者所需结果，以及存储和模型选择的适用前提。

**分析动作：** 先落实完整动作和查询定义，再按其准备请求、返回及实例：

1. **先采用已经明确的参与者与接入边界。** 按第3、4章逐个落实当前参与者怎样读取、选择和执行，核对现有协议的身份、授权、对象范围及结果，确定完整采用还是只复用部分。完整引用覆盖调用条件；只复用内部能力、数据项或分页时，说明本次入口的授权及必要适配，不把旧HTTP守卫一起带入。已确认参与者、对象范围及动作条件由前文继承，不能在本章按接口习惯重新设定。只有行为或方法名时给本次需要的候选契约，实际映射未知只保留局部核实点，不省略确定的消费需要。
2. **按消费结果形成完整查询，再组织路由与结构。** 从消费者要显示、判断、选择、筛选和继续什么，承接第3章所需读取，并将本章设计中增加的读取放回同一查询结果定义位置。定义以结果集合的消费含义划分，不以主次接口或响应外层划分；同一响应包含不同动态集合时，各自确定范围、筛选、顺序及读取边界。顺序有业务要求时，说明实际事实及比较方式怎样满足它，并列和缺失值按实际可能情况处理；业务不要求顺序时，也明确无序约定及是否由消费者排列，不让调用方猜数据库自然顺序。依据是否全量或分段确定续取、结束，不强迫所有集合分页；固定值列表采用所属完整值域即可。随后确定数据项、嵌套键、类型及必返/省略/null，完整既有查询可精确引用。查询完整相同才整体复用，只有数据项或外层相同只复用对应部分。结构在本处定义一次，实际依赖取值连同所属完整中文采用，存储不同时给映射。
3. **把动作定义完整映射为可调用契约。** 对第3章每个相关结果，给出确定的成功或拒绝响应及恢复；遗漏的情形回修动作定义，不用示例中的单一成功代替。再补传输格式、参数校验和技术错误，输入明确位置、类型、完整取值、必需/省略/null及缺省，不按表生成CRUD或照抄列可空性。每种动作总输入与结果完整后才提取真正共用部分；共用定义加明确增减应能恢复本动作全部必要信息。
4. **在唯一的场景示例区实例化契约。** 先排读取/必要续取、选择、执行和结果后读，从第3章成立的起点开始。每个示例单元包含当次调用者、对象、当前事实、请求及对应响应，得到变化后再构造下一请求；状态或关系改变后重新按定义判断资格。独立分支也自带起点与相配请求，不能只换响应或沿用另一分支的参数。通用定义及接口小节只引用这些单元，不再各自生成具体JSON。简单结果可直接按明确定义推得；涉及非直观比较器、类型/空值或多步集合变换时，先用已有只读工具对有限数据应用实际规则再采用结果，不打印预写答案自证。无需服务、迁移或另建计算文件；只有实际工具返回才称工具验证，普通推演按推演标注。所得事实代回模型、表及图，额外验收分支仍用同一过程；一处正确不能抵消另一处错误，有限实例也不证明真实实现或定义完整。

某未决业务分支不影响的接口照常给完整请求、响应和错误，变化部分就近保留条件。内部错误转换为业务含义，不直接展示供应商原始码。

涉及外部依赖时核实实际请求、返回及其业务含义；查询原结果、回调、幂等和重试均以真实能力为前提。没有原结果查询能力就不设计查单；超时结果未知时，说明等待及后续处理的条件、责任和副作用，包括可能的重复执行或费用。缺少业务处理决定时回需求，不能自行增加人工通过、强制失败或无限等待规则。

**输出及使用者：** 查询结果定义、每条接口的场景与权限、输入与完整返回、合法示例、错误和恢复，以及响应到消费者行为的映射。查询结果定义集中说明本次改变或实际依赖的范围、行为与结果结构，各读取接口直接引用；完整相同查询只定义一次，不成为独立接口索引。输入表负责类型、缺省和校验，不在两处维护相同定义。可以具体展示推荐的候选契约；若某个动作依赖未定选择，就近引用该前提，不把建议写成既有接口行为。遵守项目公共协议，HTTP、事件或回调按实际边界选择。第5、6章相互校验；不要求全部表定稿后才设计 API。

需要前后端协作且真实能力尚未齐备时，本章给出接口准备安排：可调用路由、服务端开发态 Mock、准备与真实替换的负责人、启用范围及清理条件。前端通过同一协议完成本组体验，再按领域能力逐步替换；已有真实能力直接复用，不为纯后端或普通查询强制Mock。具体实施顺序由 references/plan/task-breakdown.md 承接。

**检查与回溯：** 当前身份可调用，动作前提可达，响应足以继续，失败后有符合需求的下一步。无来源状态或操作回第3、4章，存储无法保证承诺回第5章；外部能力未证实则保留明确缺口，Mock 可操作不算能力已成立。

**批量审核贯穿例：** 提交返回 202 及批次 ID，查询返回 200 和逐条结果；处理与查询的授权时点分别明确。内部运行和等待重试合为对外 PENDING，错误码用于程序判断，文案用于解释；浏览器结果页与 API 查询地址分别定义。

### 7. 功能指标、监控与告警：观察用例结果及偏差

**输入：** 用例结果与异常、领域规则、执行和写入位置，以及现有查询、日志、告警和结果保留窗口。

**分析动作：** 先判断本次变化有无新增观测缺口。已有能力足够则引用来源，局部缺口仅补相关项；需要展开时沿用动作条件、取值定义和预期，区分业务成功、预期拒绝、系统失败、尚未结束和完成错误，再选择可靠观测位置。若此时发现新的业务审计动作，回到负责概念补齐含义及保存约定；纯技术观测编码可就近定义并说明业务对应。尚未确定是否合法的业务组合先核实实际行为，不直接当作异常口径。不能从一条一致性规则直接推导每分钟全量巡检，也不默认新增事件总线或监控平台。

**输出及使用者：** 必要性判断；需要补充时给采集或查询位置、统计口径、日志关联、告警条件及责任动作。比例说明窗口、分子分母及样本条件，积压/时延说明数量、年龄或分位值及持续条件，严重事件可单次告警；无需告警则说明观察。阈值引用需求或标明待验证初值，技术目标引用第8章。

**检查与回溯：** 结果可观察、不漏计或重计，查询和审计保留窗口相符，采集失败不视作零错误。不能无依据声称已有覆盖；发现缺口时回补相应状态、记录或采集点。

**批量审核贯穿例：** 异步路径需要系统失败和滞留观测，结果分布复用查询。一致性由事务及验收保障，排查时关联审核记录；是否新增运行巡检取决于真实风险和成本。

### 8. 非功能指标：验证设计成立的条件

**输入：** 第3章动作及分支已形成的条件、完成事实和观察预期，后续设计对它们的落实，以及从第1章起采用的性能、安全、容量、恢复、成本等约束和现有验证依据。

**分析动作：** 采用已定义动作结果及第6章实例，补观察位置和判定办法。额外验收分支也经第3、6章同一起点与实例生成过程，不在验收摘要里重新拼接事实；人工注错明确其前提和防御性用途。验证保留等既存事实的承诺须有观察目标，不存在与空结果仍按其分支成立。质量约束只展开实际影响，沿用足够则简述，规模未知给办法不编数字；未决条件继续保留，发现矛盾回修负责定义及投影。

**输出及使用者：** 必要性判断，以及相应深度的目标、措施、验证条件、限制与风险，供设计裁决和验收使用。数据迁移回第5章，协议兼容回第6章；综合配置和运行回退放文尾摘要或专项文档引用，不扩成第九主模块。

**检查与回溯：** 容量可能改变执行方式，恢复影响任务身份和状态，安全影响访问边界。验证可以证明技术选择是否成立，不能替代业务决定；未定条件下只能给条件性判定。目标不成立时回修对应设计；若必须改变业务结果，回需求决定，不能仅补“优化性能”或自加门槛。

**批量审核贯穿例：** 响应目标要求快速接收，恢复目标约束领取和租约。60秒是健康数据库及其他执行实例可工作时恢复领取的目标，不等同于整批完成，也不能用于承诺单实例停机期间自动恢复。

## 从草案到采用稿：作者与评审共用的完成标准

完整方案同时要让设计成立、让接手者能够使用。作者自检和独立评审均沿下文检查设计关系，再对照各章“输出及使用者”和统一表达标准，判断接手者能否从图中理解边界与关系、按协议准备请求和处理结果、按交接安排近期实现及验收。评审的专项维度用于定位问题，不能替代这项完成判断。

草案允许明确保留未决条件或未完成的视觉验证，已经确定的设计仍按相应输出要求表达。交付或评审结论说明哪些部分可用、哪些缺口影响哪个依赖；不能仅因有八个标题、列出接口名称或业务逻辑看似合理就宣布完整采用。缺少必要关系表达或调用契约时，修正其负责章节及下游影响；表达已有材料可以引用，不重复制作，无关章节也不展开。尚未运行验证不等同设计不成立，结构和语法通过同样不等同图稿可读或真实功能成立。

先检查本次实际依赖的定义能否直接使用：动作在相关情形有结果，属性含义完整，查询业务含义有事实承接，关系双向数量可恢复。再把图和协议读回这些定义，核对范围、条件及表示是否相同；最后用各实际实例验证演变与连续消费。实例正确不能补出未定义内容，一处正确也不能抵消另一处矛盾。缺口回修负责位置并同步实际影响，共同能力与局部未知边界保持一致。

| 相互校验 | 需要成立的关系 | 批量审核检查点 |
| --- | --- | --- |
| 目标、用例与行为 | 行为实现参与者结果，异常不改变已确认规则 | 接收不等于完成，结果找回不暗含新增历史列表 |
| 行为与领域模型 | 每个动作有责任，跨入口使用同一规则 | 单条、批量和恢复共用内容审核能力 |
| 模型与存储/协议 | 保存方式和动作承接同一模型及其前提，未决选择不因展开而变成事实 | 去重由R-04要求，唯一键是本方案实现；授权按R-05落实 |
| 存储与响应 | 协议承诺有一致的数据来源 | 汇总与明细同一快照，历史结果不随内容现状改变 |
| 结果与观测/质量 | 能发现偏差，目标有条件和判错方式 | 中断后恢复且无重复审核，不只检查仍能返回202 |

沿这条路径同时核对关键结论：依据能支持的范围是什么，当前推荐是否改变业务规则或既有契约，下游是否保留了相同前提。发现失真，修正负责的来源和受影响结果，不沿章节逐处补丁。保留关键因果和来源引用即可，不为每个字段建立追踪编号。文尾给实施与验收交接：主要用户结果及关键依赖，代表输入、真实入口、经过的服务/存储边界和最终消费者，最早要证实的判断，以及仍模拟或未验证的能力。说明相应验收范围、设计评审版本与裁决、尚未闭合前提。已有任务或评审材料直接引用，没有就简述当前安排，不为引用先造完整任务包。任务及执行状态另行维护，具体执行按 references/plan/task-breakdown.md；结构、JSON、图稿、原型和真实集成分别说明证据边界。

## 统一表达标准

### 正文、依据与取舍

每节先给结论，再用必要图、表和示例说明依据。背景一段交代，需求只引用版本与章节；证据在使用处注明文件、版本及能证明什么，长索引可放附录。关键选择可以写“本方案建议采用……，依据……，成立前提……；未定部分仅影响……”，其余章节引用，不必反复加标签。用完整短段落表达因果，同一概念全篇同名，机器字段保留原值并解释中文含义。

步骤用编号、比较用同维表格，默认不超过四列；复杂内容分节，不缩小字号。第4—6章有真实竞争选项时就近比较“问题与依据、选项、理由、代价及重新评估条件”，简单沿用说明依据即可。图后不逐句翻译整图，表下不重抄字段，模板占位提示不进入正式方案。

### 图的选择、语义与验收

图按要解释的问题选择。同一用例不固定三张图：职责交接用泳道图，边界/协调/业务对象协作用用例分析图，时间与调用竞争用时序图；简单行为可用短说明，多图须承担不同问题。

| 图 | 必须表达的内容 |
| --- | --- |
| 系统概览 | 真实系统、应用和存储边界，模块在所属容器内；沿用/修改/新增有文字或线型标记，不把业务步骤画成独立服务 |
| 用例图 | 参与者在边界外，用例在内；参与连线不表示先后，include/extend 只在语义成立时使用 |
| 领域图 | 业务概念、职责、关系名及数量；枚举属性就近列值及中文含义或引用图下定义，不用数据库字段清单代替模型 |
| ER | 物理表名+中文名、字段名+类型+中文义、PK/UK/L、可空及初值；枚举取值及中文含义可放图下字段表，图与表按字段对应；逻辑数量及业务删除规则，既有表节选标明、新表完整展示 |
| 状态机 | 初始、合法转换、触发/守卫条件及实际终态，含相关重试与恢复；图、转换表和 API 映射一致，不新增未要求的取消状态 |
| 时序/泳道 | 负责主体、交接、先后、条件和关键失败分支；时间向下或按泳道内流程清晰展开，事务边界明确 |

领域图从第4章每条关系的双向定义生成；画完把两端数量读回同样两句话，核对作用范围及何时为零，不在画线时重新猜数。ER映射物理表时承接完整记录范围和同一关系角色，不能用另一种关系替代；状态图表达同一对象的生命周期。ER的L仅为逻辑关联，历史ID存在与目标可查询分别说明；记法未知先核实。联合唯一键列完整列组，大图拆总览与分表细节，不缩字塞图。

优先项目已有工具和渲染方式。流程、状态和时序可用已有 Mermaid；系统、领域和复杂 ER 在中文长字段或布局难读时，使用已就绪的 Graphviz、PlantUML 或可编辑工具。标准 UML 用例图需要相应边界和图形支持，等价表达应说明。可维护图源必须保留，不要求所有 Agent 手写 SVG，也不强制所有项目额外导出两种格式。

配套示例的结构图使用本地 Graphviz WASM，协作泳道以生成脚本维护，正文嵌 PNG、链接 SVG 放大。源修改后重新生成，图片与源保持一致。逐张打开产物，检查中文、裁切、连线、图例和正常正文宽度；文字不清先拆图或调整布局，不靠缩小字体。约十二个主要节点是拆图检查信号，非硬限制。图源语法通过、图片存在均不代表视觉合格，独立图片检查与实际 Markdown 阅读器检查分别报告。

### API 的阅读格式

本章先定义协议，再集中展示实例。每接口小节给场景与权限、方法/路径、完整参数与返回结构、结果条件、错误和恢复；共用定义写一处，接口精确引用及说明差异。具体请求/响应JSON只放章内统一的“场景示例与连续消费”区，每个单元有明确起点及相配调用；可以覆盖多个接口，接口就近引用单元。关键命令和不同结果仍有完整合法示例，但不在每个接口再复制一套。公共认证、ID、时间、分页、空值引用项目约定；参数表可用四列，返回表可用三列，嵌套字段按路径展开。

字段和嵌套结构按第6章形成，类型、必返/可空、取值、默认及约束在定义处完整，示例消费它而不代替它。有限取值连同中文采用所属概念或契约的完整定义，新增与沿用部分不丢失；引用来源缺少的说明在负责位置补齐。JSON合法，数量、编码、状态一致。请求级错误与单项失败分开，异步接收与完成分开，UUID不为排版改成假ID。

工具用于核实所选规则，不按图或样本数量强制调用。例如选定UTF-8字节序时，可在现有终端执行下面的局部比较；其他比较器应采用其真实规则，不能用直觉顺序替代。此代码只说明操作方法，不是项目业务或排序建议，也不另存脚本：

```sh
python3 - <<'PY'
values = ['Z', 'Å', 'A']
print(sorted(values, key=lambda value: value.encode('utf-8')))
PY
```

下面是**独立虚构的格式片段，不是业务或分页方案建议**：假设已有记录查询及可空的末次变更，消费者要显示当前状态及上次状态变化。既有机器值不变，补充中文；嵌套结构在此确定，而不是仅说“包含前后状态”：

```ts
type RecordState = 'DRAFT' | 'PUBLISHED'; // DRAFT：草稿；PUBLISHED：已发布
type StateSnapshot = { state: RecordState };
type RecordBrief = {
  id: string; // UUID，必返
  state: RecordState;
  lastChange: { before: StateSnapshot | null; after: StateSnapshot } | null;
  // 所有键必返；lastChange=null表示无变更记录；before=null表示创建前无对象。
};
```

授权调用者只读本租户记录，按已有 `id ASC` 排序，结果为 `{items:RecordBrief[],continuationToken:string|null}`。`pageSize` 可选整数1—50、默认10；`after` 可选不透明字符串，首查省略；显式null、非法类型/范围或与本查询不匹配的标识均400。只有外层相同不能据此复用排序。

演示初始集合有本租户的两条记录（ID末位1、2）和另一租户的一条记录（ID末位3）。先限定租户、再排序，符合条件的两条以pageSize=1分成下面两页；源集合里的第三条不会出现在响应中。这些是设计数据，不是实际查询记录。

```http
GET /records?pageSize=1
```

```json
{"items":[{"id":"10000000-0000-4000-8000-000000000001","state":"DRAFT","lastChange":null}],"continuationToken":"sample-token-1"}
```

调用者尚未找到目标且返回标识非空，将**响应的 `continuationToken` 值**放入**下一请求的 `after`**，保留原范围、筛选及pageSize。示意标识只供读格式，不是真实生产凭证：

```http
GET /records?pageSize=1&after=sample-token-1
```

```json
{"items":[{"id":"10000000-0000-4000-8000-000000000002","state":"PUBLISHED","lastChange":{"before":{"state":"DRAFT"},"after":{"state":"PUBLISHED"}}}],"continuationToken":null}
```

第二次返回null，结束读取；用户选择第二项后以其响应 `id` 构造 `GET /records/10000000-0000-4000-8000-000000000002`。这里同时检验了首次参数来源、返回值到不同名输入字段的传递、结束以及选择到详情；空集合为 `items:[]` 且标识为null。实际方案采用自己的查询与字段，偏移分页、单次完整读取等以其实际契约走读，不照搬本片段，也不把设计推演声称为真实调用。

按实际需要解释幂等作用域、内容比较、有效期、并发冲突及重复消费保护。协议变化列明实际消费者和兼容方式；开发态 Mock 由服务端按同一协议提供，前端通过真实请求完成本组体验，再逐步替换模拟。模拟成功与外部能力、真实业务成立的证据分开。

### 观测与验证的表达

指标标签避免用户或内容 ID 等无限增长的取值；日志关联必要排查标识，保留隐私和敏感信息边界。告警写清责任与实际动作，预期业务冲突不全部算系统故障。每个目标或阈值有需求、推导或候选初值来源，未验证不得写成达标事实。
