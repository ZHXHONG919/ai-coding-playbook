# 实现落地阶段

> 按当前约定交付完整路径；实现步骤可以调整，用户语义不能随工程分工改变。职责与交接见 `references/delivery/agent-delivery-flow.md`，正式核验见 `references/stages/review.md`。

## 开始前

- 用户要求开始实现、按方案落地或修复即可在授权范围内执行；已有确认和授权直接复用。只有讨论方案时不改代码，不为普通改动补整套文档。
- 读取目标项目事实、相关代码、当前结果约定与各区块最新来源、可改范围。需要 Goal 时按 `references/stages/goal-handoff.md` 准备；统一使用 schema 3。Goal 的执行和恢复读 `skills/goal-execute/SKILL.md`。
- Git 写操作遵守 `references/git-safety.md`。候选规则未获应用授权时在隔离工作树修改，不改已安装源或全局链接。
- 第三方工具按 `references/delivery/tooling-prerequisites.md` 准备。尽早核实目标环境版本、代表数据和权限；开发默认用本地或可丢弃环境，真实 provider 验证属于本次范围且已授权时执行，并说明配置、成本及证明边界。

## 沿一条路径实现

1. 同一 owner 从当前结果推进到集成和返修。先从约定选判错样本，再沿真实生产者、转换、消费者及写后读入口核实事实；上游用 UUID，就不能用自造数字 mock 证明转换正确。
2. 只展开当前与近期工程任务。共享规则由主线程判断，稳定边界内可以委派；交接包含当前约定、事实、范围、判错样本和返回要求，不默认携带全部历史。
3. 在当前结果内尽早跑通小的真实路径，再扩展角色、入口和异常状态。mock 只隔离明确边界，保留真实能力和集成检查；局部缺口按中央流程处理，不停掉无依赖工作。
4. 对改变的行为运行最小有效自测，观察真实结果。方法见 `skills/test-scope-analysis/SKILL.md`；纯格式不新增镜像测试，业务语义变化不能因文件是 Markdown 就免检。
5. schema 3 技术任务通过后记 `done` 并继续；正式验证和 CR 面向完整结果及共享基础，不能将任务自测冒充结果验收。

共享基础在消费者依赖新规则前核验；完整路径可运行时固定版本做独立验证与 CR。主线程裁决缺陷、误报和新建议，修复后只补受影响检查；Git 检查点不代表验收。

## 有已确认界面时

实现者与修复者先实际打开当前动作/区块的有效采用稿。明确必须保持的页面层级、打开与返回方式、对象上下文、控件关系，以及允许复用的生产样式；“沿用组件”“原生适配”不能解释成改变信息结构或交互容器。

优先复用确认的结构、样式和组件。首个代表页面或弹层可运行后，以相同视口、角色、状态及代表数据对照，裁决具体差异是否符合授权，再扩展共享实现。截图必须用于判断，不以“截图已留”代替通过。无法完成校准时保留缺口，不扩散未验证布局；独立工作继续。

目标项目已安装 impeccable 时按问题选择 audit / critique / polish，用户认可的局部调整优先于旧整页稿和通用审美建议。路径核验分别证明视觉还原、交互一致、业务正确；修复后只核对受影响状态和复用入口，不反复制造全套截图。证据方法见 `references/delivery/evidence-driven-delivery.md`。

## 中途修订与影响传播

用户主动修订时先更新单一业务决定及受影响结果约定、来源指针和派生契约；只在同步期间暂停依赖旧规则的工作，然后继续。已经授权的新要求不重复申请确认。Agent 可自主选择实现细节，但不能增加产品限制、改变已确认页面形态，或用 reviewer 偏好替换用户决定。

本次代码变化要映射到受影响结果；共享规则沿生产者、消费者和恢复入口传播。用户约定改变时，即使代码未改，旧约定下的检查也不再证明当前结果。历史证据保留原版本，只定向补验补审；未受影响的检查继续复用。不能修改历史“通过”记录或只刷新哈希冒充重验。

## 记录与收尾

无 Goal 时复用现有任务记录或对话；schema 3 Goal 在任务边界记录进度，在运行记录保存版本差异、结果检查和 CR，状态文件只作执行索引。技术任务不再逐项 `accepted`，不另写逐任务验收报告。

收尾核对全部约定结果、完整改动与当前有效证据，真实能力缺口不能变成后续建议而消失。最终说明交付行为、验证、审查和限制；代码验收、测试发布、生产发布分别报告。用户要求的真实环境验收不能擅自推到发布阶段，部署、迁移、推送等继续遵守已有授权和项目 SOP。
