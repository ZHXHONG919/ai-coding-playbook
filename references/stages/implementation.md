# 实现落地阶段

> 按已确认意图改代码，让最小真实路径尽早可验证。节点职责与中文交接提示见 `references/delivery/agent-delivery-flow.md`。

## 开始前

- 用户要求开始实现、按方案落地或直接修复即可进入；只有讨论方案/询问能否开工时不改代码。
- 读取目标项目事实、相关代码、最新确认约束、可改范围；已有任务/方案就复用，不为简单改动补整套文档。
- Git 写操作前读 `references/git-safety.md`。安装、同步或发布范围以用户授权为准；规则仓库存在实时软链接且用户要求暂不应用时，在独立工作树开发，不能改已安装源目录。
- 需要结构化跨上下文恢复或用户要求 Goal 时，先按 `references/stages/goal-handoff.md` 准备执行包；已有 Goal 按 `skills/goal-execute/SKILL.md` 恢复。并非接触 API、异步或数据库就必须建 Goal。
- 涉及第三方工具时读 `references/delivery/tooling-prerequisites.md`；涉及界面或用户可见结果时读 `references/delivery/evidence-driven-delivery.md`，继承已确认基线和证据要求。

## 实现与自测

交接信息、自主决策与局部缺口统一按 `references/delivery/agent-delivery-flow.md`；每个任务先核对其实际需要的输入，使用已验证契约隔离暂缺能力时，保持真实集成任务和验收要求。

1. 沿实际生产者、转换、消费者、写入和读回路径确认契约。上游标识是 UUID 就用 UUID 样例，不用自己设计的数字 mock 证明 DTO 正确。
2. 主线程决定亲自实现、委派或混合；共享规则和业务口径保留主线程判断，机械或独立模块可以并行。按中央交接信息给 worker 当前结果、约束、事实版本、范围、验证和返回要求；不只给文档目录和一句功能名。
3. 按已确认任务顺序实现，在同一功能批次尽早走通最小真实路径，再扩展页面、角色和异常分支。前端先 mock 可以验证界面；应用自身的真实装配与读写仍需尽早替换。
4. 运行最小有效自测：改变的行为、风险反例、真实入口/观测点、预期和方法应对应。检查规则见 `skills/test-scope-analysis/SKILL.md`；纯格式小改不写镜像实现的测试，语义规则改动不能因扩展名是 Markdown 就免检。
5. 自测通过记为 `implemented`。实现和自测可共用简短记录；普通任务不强制另派 validator 和 reviewer。

## 审查边界

以 `references/stages/review.md` 为唯一细则：

- 普通任务自测通过后可继续，组成可验收功能批次后独立验证和 CR。
- 改变后续依赖的共享规则时，把该有限范围单列基础批次，在依赖方开始前审查。调用既有权限服务或新增遵循旧契约的字段不自动属于基础改动。
- 用户/项目明确逐任务审查时遵守；轻量单次改动可按风险自审并说明方式。
- 批次验证与 CR 可并行，必须基于同一个固定版本。主线程核实发现，再决定真实缺陷、误报或后续建议；有缺陷按问题族和影响域修复复核。
- 全部批次和最终增量被覆盖、验收通过，才标 `accepted` / 完成。Git 检查点不等于验收。

## 界面和中途变更

有已确认界面时，实现者和修复者先实际打开同一采用稿，按编号读取版本、页面状态、参考视口、视觉/交互保留项及允许差异。交接规则只在现有 ui-flow / 原型说明维护一处，具体要求见 `references/delivery/evidence-driven-delivery.md`。

优先迁移采用稿的结构、样式与可复用组件，再接真实数据；保留确认的布局、字号层级、密度、关键控件及主路径、权限和状态。新页面、大改版或共享布局首次可运行时，同视口同状态对照代表页面后再扩展，作为当前任务自测。尚无法运行对照时保留校准缺口，不把同一未验证布局扩散到其他页面；无依赖工作可继续。

目标项目已安装 impeccable 时按实际风险选择 audit / critique / polish；已确认视觉决定优先于通用审美建议。修复溢出、遮挡等技术问题时保持确认效果，局部文案授权不扩大为重新设计；不每个中间任务重复完整截图和审计。

批次统一采集最终证据，分别陈述视觉还原、交互一致、业务正确；视觉未验不能以源码 Fixed 或测试通过标为整体还原完成。验证和 CR 可以在同一版本分别完成，不强制另开“零阻塞确认”报告。修复影响界面后复验受影响状态，扩大共同状态规则时检查其他消费者。采集方式失败按证据规则切换，不能悄悄降低证据等级。

用户主动修改要求时区分对当前验收/依赖有影响的新约束和可后续讨论的建议。前者先更新单一业务决定及其派生契约，仅在同步期间暂停受影响任务，然后继续；后者记录 owner 和处理时点，其余工作继续。已经授权的新要求不重复申请确认；“更安全”或 reviewer 意见不能覆盖用户决定。Agent 补足执行细节时注明自身决策依据，不把它冒充为用户确认。

## 记录与收尾

没有 Goal 时在现有 tasks 或对话中记录“任务 / 所属批次 / implemented或accepted / 自测证据 / CR覆盖 / 缺口”；已有 Goal 时只更新 `status.yaml` 和必要报告指针，不复制多份进度表。

最终回答改动、为什么这样改、如何验证、审查结果和实际限制。尚未验收不能只写“代码完成”；代码验收与发布准备度分别报告，未授权不安装、不部署、不推送。
