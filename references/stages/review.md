# 代码审查与结果核验

> 独立验证回答“用户结果是否成立”，CR 回答“实现还有什么风险”。二者不能互相替代，也不靠重复检查或报告数量证明质量。

任务统一按完整用户路径及共享基础核验，技术任务只记进度。Goal 使用 schema 3；显式审查请求按用户范围执行，不借本规则重建执行包。

## 何时正式核验

| 时机 | 动作 | 对继续工作的影响 |
| --- | --- | --- |
| 普通技术步骤完成 | 实现者做必要自测，通过可记 `done` | 继续当前路径；失败只阻止依赖失败行为的工作 |
| 新的高风险共享基础将被依赖 | 独立验证规则及生产/消费入口，并做专项 CR | 当前基础缺陷先修，消费者不能依赖未核实语义 |
| 一条完整用户路径可运行 | 固定版本做独立验证与 CR | 未通过检查的结果不能宣称完成，独立路径可继续 |
| 最终交付 | 核对全部结果、全量差异与历史证据，补查未覆盖增量 | 必需结果或交付改动仍有缺口时不能整体完成 |

不因文件属于 API、数据库或前端就提前审查，也不把每个小任务改名为结果。未建 Goal 的低影响单次改动可按风险自审并说明方式；已约定独立核验、用户或项目要求更严时遵守。

## 先独立观测，再看实现结论

1. 验证者可以先收启动命令、版本、入口和必要环境等中性执行事实。先读当前结果约定及动作/区块对应的最新来源，推导预期与判错样本；旧代码或旧测试的现状不自动成为要求，历史原型不能覆盖已认可修订。来源冲突先由主线程依据已有决定裁决，不能按“测试已绿”选口径。
2. 选择能区分最可能错误实现的样本：定位对象用多个对象和无关数据，复用入口用成对入口，权限用允许与拒绝身份。说明预期来自哪里，不复制实现常量或实现者的成功结论。
3. 从应用真实入口执行并读取实际结果。不得手造业务结果或直接写入最终记录替代应用执行；模拟边界只证明该边界以内的行为。并发、事务、权限、模型效果等需要各自有效证据。
4. 完成独立观测后再读实现报告中的自测和成功结论，结合 CR 检查分歧、遗漏及证据充分性；不能用实现者的解释覆盖实际观测或当前约定。

检查方法见 `skills/test-scope-analysis/SKILL.md`；证据要求见 `references/delivery/evidence-driven-delivery.md`。

## 固定版本，独立验证与 CR

记录基线与待验版本，以及当前约定和环境配置。未提交改动可以用含新增文件的固定快照，不为检查强制提交。验证与 CR 可在同一版本并行，也可由同一独立 Agent 承担；共享写入环境需隔离或顺序执行，不默认重跑全部命令。

CR 独立检查差异、实际调用方、共享规则的生产/消费/恢复入口、测试判错能力和需求覆盖；不能只读实现报告。检查期间冻结该范围，独立工作可继续；必须修改时重新标定版本，只使受影响结论失效。

一次运行记录可以承载验证、CR、裁决与复核。schema 3 用 `checks` 证明对应 `contract_hash` 的结果，用 `review` 保存独立审查；`changes` 必须覆盖该轮完整差异并映射受影响结果。当前结果有效性由历史与本轮记录推导，不另填结果通过状态。字段和固定版本要求见 `references/delivery/goal-v3.md`。

## 发现与裁决

每条发现给出位置、触发条件、违反的当前约定、实际影响和可复查依据；推断须注明不确定性。

| 级别 | 判定依据 |
| --- | --- |
| P0 | 证据充分的严重数据破坏、权限绕过、不可恢复操作或核心服务故障 |
| P1 | 当前结果或契约不成立、缺陷会传播到依赖，或关键风险仍缺必要证据 |
| P2 | 不影响当前验收、数据、权限或状态正确性的维护、可读性或体验建议 |

主线程选择修复、合并同根因、待核实、拒绝并反证、非阻塞后续处理。是否阻塞看真实影响，不能靠改级别跳过缺陷；也不能把偏好、缺少某个文件或无具体触发的设想写成阻塞。后续建议记 owner、影响与处理点，不无限返工。审查者不能以“更安全”替用户改变语义，普通实现取舍不自动触发新一轮产品审批。

## 增量修复与历史证据

- 修复先覆盖原失败路径，再核对同一规则的消费者、合法/非法分支、持久化与恢复。小 diff 也可能影响多个结果。
- 同类再次出现，先查共享根因及全部受影响入口，再统一修复；不逐个打补丁，不靠轮次上限通过或不断换 reviewer 延长循环。
- 每轮完整改动都映射受影响结果。共享基础变化沿依赖传播，消费者不能沿用旧基础下的通过结论；根据实际影响补验补审。影响难以隔离或项目要求时扩大回归。
- 用户修订使受影响结果约定改变，旧检查保留历史意义但不能证明当前约定。未受影响证据复用；历史记录不回写成新版本，不能仅更新哈希。
- 最终比较历史核验版本与交付版本：新增行为补验、未审运行改动补审、纯报告改动核对事实。保留已有有效覆盖，不把每个新文件都解释为全部结果失效，也不让最后一次小范围 CR 覆盖此前未审改动。

## 前端与原型一致性

核验当前动作/区块的有效来源，同视口、角色、状态和代表数据比较；先确认页面层级、打开方式、取消返回、对象上下文和控件关系，再判断视觉差异。生产组件和配色可按授权保留，不能据此保留已被新需求替换的信息结构。

分别给出视觉还原、交互一致、业务正确的证据。截图不能证明点击与返回，源码 `Fixed` 不能证明实际显示；首个代表页面通过也不能替代复用入口检查。用户选择自己验证时交接采用依据、实现入口和待验点，收到实际结果后再更新检查，不提前写通过。

小文案或局部样式可直接核对现有页面，不强制补原型。已安装 impeccable 时按风险选择 `audit` 或 `critique`，不为安装阻塞审查；通用审美建议不能覆盖用户认可调整。修复未影响的界面证据直接复用，改变了呈现或行为才检查对应状态。

## 输出

简述结果范围、版本、独立预期与实际、CR 发现及主线程裁决、缺口和复核范围。无阻塞时仅说明“在已审范围内未发现阻塞问题”；结果通过仍需对应行为证据，整体完成仍需最终增量覆盖。执行策略的取舍引用现有记录，见 `references/delivery/execution-evidence.md`，不额外建统计报告。
