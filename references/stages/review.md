# 代码审查阶段

> 目标：用独立判断发现真实风险，在会影响后续实现或交付的时点检查；审查报告没有新问题，不等于功能已经验证。

## 审查时机

显式要求审查时执行用户指定范围。开发流程默认按功能批次审查（`functional_batch`）；只有用户或项目明确选择逐片审查（`per_slice`）时才逐片执行。已有 Goal 从自身审查策略读取约定，迁移策略时先更新其执行契约，不能一边沿用旧完成状态一边临时跳过检查。

| 时机 | 执行动作 | 何时阻止继续 |
| --- | --- | --- |
| 普通任务实现后 | 实现者按行为检查单自测，记录“已实现，待批次验收”，按既有 Git 授权与项目规则提交功能分支检查点 | 自测失败的任务不算通过；只阻止依赖失败行为的后续任务 |
| 后续任务依赖的关键基础形成 | 针对改变的共享契约、权限、状态、身份、计费、并发或迁移做专项审查 | 经裁决的缺陷会传播到后续实现，必须先修 |
| 一个完整功能可运行 | 针对固定版本并行做功能验证和正式 CR，汇总后集中修复 | 验收或交付阻塞未解决，不能宣布该批次验收完成 |
| 交付收尾 | 核对所有批次验收、修复结果，以及上次审查后新增改动的覆盖 | 尚有交付阻塞或未覆盖的交付改动 |

“关键基础”取决于本次改变的规则及其依赖，不因文件属于 API、数据库或前端就自动触发。复用且未改变的基础不重复审查。功能批次按可操作的用户路径或共享能力预先约定，不能把每个小任务重新命名成一个批次。

## 固定范围，验证与 CR 并行

1. 确定范围和版本：指定 diff、功能批次或提交范围；记录基线与待审提交。未提交改动用包含新增文件的固定差异副本或内容摘要标识，不要求为了审查先提交。
2. 提供已确认行为、自测检查单、实际改动和已有验证结果。审查者从生产入口、调用方及契约独立判断，不只阅读实现报告。
3. 验证者运行覆盖实际行为的检查；审查者检查实现、遗漏风险及测试是否足以证明。两者可读同一固定版本并行工作，不默认由审查者重跑全部命令。共享环境有写入冲突时隔离或顺序执行。
4. 该范围审查期间冻结修改；独立范围的工作可继续。必须修改待审范围时，重新标定版本，仅使受影响结论失效，避免同时改代码、验旧代码、审旧代码。
5. 主线程汇总并去重测试失败与 CR 发现，做出裁决，再集中修复。一次批次报告可同时承载验证结果、CR、修复和最终证据，不要求每个任务另建确认文件。

按 `skills/test-scope-analysis/SKILL.md` 选择检查；按 `references/delivery/evidence-driven-delivery.md` 判断证据可信度。角色视角用于选择专项风险，不要求为每个角色另开 Agent 或另写报告。

## 发现、裁决与优先级

每条发现应给出位置、触发条件、已确认规则、实际影响和可复查依据。需要推断时标明不确定性；不能把未验证的工程偏好直接写成缺陷。

| 级别 | 判定依据 |
| --- | --- |
| P0 | 可复现或证据充分的严重数据破坏、权限绕过、不可恢复操作或核心服务故障 |
| P1 | 违反当前验收或契约、会传播到依赖的正确性问题，或缺少证明关键风险已受控的必要证据 |
| P2 | 不影响当前验收、数据、权限、状态正确性的可维护性、可读性或体验改进 |

主线程对每条发现选择：**接受修复、合并同根因、证据不足待核实、拒绝并给反证、非阻塞后续处理**。审查者负责提出独立证据，主线程负责最终裁决；不能照单全收，也不能为了通过而无依据降级。是否阻塞推进或交付由实际影响决定，严重级别标签本身不替代判断。与最新用户口径冲突时回查决定来源，由主线程按自主推进约定解决；不能用更严格实现替用户改需求，也不把普通取舍自动转为用户审批。

缺少某个测试文件或截图不自动构成 P1；先说明尚未被现有证据证明的关键行为。风格建议和无具体触发依据的设想不得持续阻止交付。

## 修复与复审

- 首次修复检查原问题及其直接影响：相同规则的调用方、合法/非法分支、状态、持久化与恢复路径。代码改动小不代表影响范围小。
- **同类问题再次出现，或修复引入新的同类失败时，停止逐个补丁。** 先列共享规则、生产者/消费者、关键状态转换、违反规则的反例，再选择统一修复。无需自动重写完整方案；涉及业务口径或设计边界变化时才同步相关方案。
- 修复后重跑原失败路径和受影响检查，Reviewer 定向核对原发现及影响范围。只有公共契约、设计或影响范围扩大时才扩大复审，不每次重审全功能。
- 轮次预算用于触发主线程根因分析或调整方法，不自动转为人工介入，不能把真实缺陷到达轮数视作已通过，也不能靠不断换 Reviewer 延长同一循环。
- 最终比较审查版本与交付版本：新增行为补测、未审运行改动补审、纯报告变更核对事实即可。审查覆盖与验证覆盖分别确认，不能互相替代。

## 前端与原型一致性

实现时已对首个可运行代表页面做基线校准；完整界面批次再对照同一采用稿，分别记录视觉还原、交互一致、业务正确的结果与证据。比较采用稿和实现的相同视口、角色、状态及代表数据，检查主路径、操作条件、错误态及信息层级。具体方法见 `references/delivery/evidence-driven-delivery.md`。

`Fixed` 只表示已修改，只有对应运行观测通过才可写该项验收通过；源码对照不能证明视觉还原。浏览器验收未做就标“还原待验收”，并保留范围和原因。用户选择自己验证时交接采用稿、实现入口及待验点，不把计划中的人工验证记成已通过。

- 小范围文案、样式、单字段或局部状态变化可直接核对现有页面，不强制补原型；无已确认基线时说明采用的现有行为与范围。
- 主路径、审核对象、权限、状态或 API/ViewModel 契约有未确认变化时，先收口该行为；视觉建议不能覆盖已确认产品规则，也不能擅自更换已确认的布局、字体层级、密度或组件形态。
- 目标项目已安装 impeccable 时按本次风险选择 `audit` 或 `critique`，复用同一界面批次结果。未安装不阻止审查，也不为此要求安装。
- 修复没有改变已验证界面行为时复用证据；改变了主路径或呈现时，仅重查受影响状态。无需每个 fixer 重做整套视觉审查。

## 输出

简述范围/版本、阻塞发现、主线程裁决、验证缺口和复审范围。无阻塞时写“在已审范围内未发现阻塞问题”，不要承诺零缺陷。批次验收完成还需有对应功能验证，最终交付还需覆盖其后的增量。

需要分析执行策略时，在已有执行记录中引用本次裁决及复审理由，遵循 `references/delivery/execution-evidence.md`。同根因的多条 finding 合为问题族，避免把评论数量当成缺陷数量。
