# Bugfix / 排障阶段

> 目标：先复现和定位，再做最小修复；每次只尝试一个主要假设。

问题可以来自对话、工单、截图、录屏、日志、监控、测试失败、代码审查或数据异常。本阶段不绑定任何具体问题平台；开始前必须读取 `references/delivery/evidence-driven-delivery.md`，按统一问题受理信息和证据等级处理。

## 角色视角

排障阶段默认站在 Incident Commander、Debug Owner 和回归验证负责人视角：

- Incident Commander：判断影响范围、优先级、是否需要止血、回滚或暂停发布。
- Debug Owner：基于证据提出假设，每次只验证一个主要假设。
- 回归验证负责人：确认修复覆盖原问题，并检查相邻路径是否被破坏。

复杂故障按需读取 `references/plan/role-lens.md`。

## 流程

1. 把原始输入归一化为问题来源、实际结果、期望结果、环境、角色、复现步骤、父子关系和证据等级。
2. 批量问题先展开全部父子问题并冻结台账，再按页面、角色、接口和共享根因聚类；不要逐条重复启动环境。
3. 收集当前行为证据、最近变更、相关代码和日志，形成候选原因列表。
4. 按概率和风险排序，每次只验证一个主要假设。
5. 优先做低风险、小范围、可验证的修复；非问题和历史已修复不得统一进入代码修改。
6. 先复现原问题并运行有效自测；基础依赖前或功能批次可验收时，固定版本做独立验证与 CR，按 `references/stages/review.md` 裁决和复核。全量回归只在共享改动的影响无法可靠隔离、项目明确要求或交付风险需要时运行，不因 Goal、批量或收尾标签自动触发。
7. 按原复现路径验证，并检查相邻角色、端、读写路径和状态是否被破坏。
8. 用户授权状态回写且来源支持时批量写回并读回确认；否则在当前任务记录和最终回复交付结果。
9. 验证成功后停止；不要混入无关重构。
10. 如果无法复现，先给证据缺口和下一步观测点，不要直接猜修。

## 证据与耗时控制

- 用户可见界面问题默认需要运行态视觉证据；后端、并发、事务和数据问题使用测试、接口或数据证据，不强制截图。
- 历史已修复只要求当前路径验证，不要求重新制造修改前现场。
- 同一页面的多个问题允许共享截图和登录过程，但每条问题必须有独立结论。
- 界面自动化最多尝试两种稳定定位方式，每种方式最多两次完整尝试；连续两次同类失败立即更换采集手段。降级不得降低证据等级：E2/E3 问题缺少等价运行态或视觉证据时必须登记人工介入或阻塞，接口/数据证据只能补充。
- 代码审查后只重跑受影响测试；是否全量回归由改动风险和项目门禁决定，不能把单个低风险局部问题升级成整库回归。

涉及 Git 写操作时必须先读 `references/git-safety.md`。排障可以执行只读检查和 `git fetch`，但不得为了“先同步主干”自动 `pull`、`merge/rebase main` 或使用 `--autostash`。

## 输出

- 根因或最可能原因。
- 影响范围和是否需要止血。
- 修改内容。
- 验证方式。
- 如果无法确认根因，说明还需要哪些信息。
