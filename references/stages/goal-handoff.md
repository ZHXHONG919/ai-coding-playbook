# Goal 执行交接

将已确认需求转为可恢复执行输入。轻量改动直接实现，不因有 API / 数据库就建 Goal。Goal 创建和恢复统一使用本页说明的 schema 3。

## 开工前真正需要确定的事

- 已有实施授权；全部用户结果、非目标、交付与发布边界明确，不能只列首条路径。
- 每个结果说明入口、操作、对象/上下文、可观察结果和至少一种容易误实现的解释。涉及界面时按区块/动作指定当前有效来源，保留项和允许差异有依据。
- 先识别会影响后续实现的共享权限、身份、计费、状态等规则，并审查其必要设计；其真实基础能力验证通过后再推进依赖方。其余工程任务可滚动细化。
- 当前路径事实与必要工具可用；局部未知有稳定协议、责任人和回收点。缺口可隔离不等于可以从最终交付中删除。
- 一个 owner 对完整路径负责，写入分工明确，独立验证/CR 可执行。复杂方案沿用已有 design CR，不再要求同一批准。

## 最小执行包

在现有需求目录的 `.goal/` 中从 `templates/goal-v3/` 取模板：

| 文件 | 职责 | 何时创建 |
| --- | --- | --- |
| `goal.yaml` | 所有结果、当前决定/来源、依赖、最近要做的工程任务 | 开工；引用已有需求与原型，不复制整包文档 |
| `status.yaml` | 唯一执行索引：任务进度、有序核验记录、下一动作与缺口 | 开工；结果通过由证据派生，不另填一份通过表 |
| `runs/<ID>.yaml` | 一个版本增量的影响、验证、独立 CR 与证据引用 | 该轮核验时；不为每个技术任务建报告 |

快照及内容由脚本按需产生，不手写目录清单。已有工具、mock、风险台账直接引用；没有相关事项不生成空表。`tasks.md` 可保留方案的取舍与说明，进入 Goal 后不再维护一份相同任务状态。仅创建当前需要的文件。

## 组织与检查

1. 按 `references/plan/task-breakdown.md` 列全结果，展开首条真实路径及近期依赖；后续只展开所需工程步骤。
2. 逐结果核对当前来源。两处相似按钮可能指向不同对象或页面，不能以技术任务的概括代替已确认动作。
3. `goal.yaml` 记录可解析的 Git 基线，`status.yaml` 初始化未完成状态。最终检查覆盖整个基线差异，包括新文件、删除和核验后修复。
4. 执行 `ruby <playbook-root>/scripts/check-goal.rb <goal-dir>`。脚本检查结构和版本一致性，不代替对开工条件及业务语义的判断。
5. 按 `skills/goal-execute/SKILL.md` 连续执行，具体字段与命令只在 `references/delivery/goal-v3.md` 定义。

用户主动修正时，先更新当前决定与受影响来源；旧证据保留为历史，不支持新约定。取消已承诺结果必须有用户依据，不能通过删结果来让检查变绿。局部能力不可用时推进可隔离工作，如实保留必需缺口，不自动重新开启产品问答。
