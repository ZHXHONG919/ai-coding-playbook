# 需求理解阶段

> 目标：把模糊诉求收敛成可讨论的业务问题、边界和验收口径。不要急着设计表、接口或任务。

## 角色视角

需求阶段默认站在业务负责人、产品负责人和领域建模者视角：

- 业务负责人：判断真实业务问题、价值、影响范围和成功标准。
- 产品负责人：收敛使用场景、用户入口、非目标和验收口径。
- 领域建模者：识别核心概念雏形，避免过早落到表、接口或任务。

复杂需求按需读取 `references/plan/role-lens.md`。

## 触发

- 用户说：梳理需求、理解需求、先讨论、帮我分析一下、这个功能要怎么做。
- 用户描述了业务目标，但还没有明确方案。

## 工作方式

1. 先读目标项目事实：README、AGENTS、相关 docs、已有实现和旧方案。
2. 区分用户明确说的、代码里读到的、AI 推断的、待确认的。
3. 用业务、产品、领域建模三个视角检查是否遗漏边界。
4. 输出可讨论的需求草案，不直接进入方案或实现。
5. 复杂需求进入方案前，必须转入 `references/stages/requirement-confirmation.md` 做需求确认。

## 从用户意图写成功标准

先完成这句话：**谁，在什么场景，通过哪个入口完成什么操作，最终在哪里看到或使用什么结果。** 这条成功场景是方案与验收的共同输入。

| 目标 | 可观察的成功结果 | 不足以证明成功 |
| --- | --- | --- |
| 修改生成提示词 | 保存的新内容进入真实生成请求，能追溯本次使用版本 | 编辑器能保存、预览显示文字 |
| 提交活动审核 | 员工提交后，审核员读到同一份完整方案并能处理 | 按钮存在、单个接口返回 200 |
| 收起面板 | 点击后内容实际消失，输入区仍可操作，返回状态符合约定 | 源码出现 collapsed、结构断言通过 |

按本轮风险补最有区分力的失败/恢复例子，不为每个需求套固定测试数量。明确数据由谁拥有、维护、消费，以及当前是新开发还是已经上线；不能把“沿用旧页面”推导成新资产的归属事实。

## 输出至少包含

| 部分 | 要求 |
| --- | --- |
| 业务目标 | 用户要解决什么问题，成功后有什么变化 |
| 非目标 | 本轮明确不做什么，避免范围膨胀 |
| 使用场景 | 谁在什么情况下使用，触发入口是什么 |
| 输入输出 | 系统接收什么，产出什么，产物给谁用 |
| 约束 | 技术栈、数据来源、权限、性能、时间边界 |
| 待确认 | 不确认会影响方案方向的问题 |

## 阶段出口

- 普通小改：已有明确范围、成功结果和用户授权即可进入方案或实现，不重复等待同一句确认。
- 复杂需求：需求分析的出口是需求确认，不是方案设计。
- 需求阶段提出的问题必须在需求阶段处理；如果问题会影响业务边界、产物契约、审核对象、数据写入时机、状态流、同步边界或验收口径，不能写成“方案阶段再定”。
- 多轮对话后，在 `requirements.md` 或项目等价文档维护唯一当前业务决策；方案、UI Flow 和任务引用决策 ID。细则见 `references/plan/decision-table.md`。

## 禁止

- 不要把需求阶段写成技术选型。
- 不要把缺失信息假装成事实。
- 不要因为用户提了一个实现想法，就跳过业务目标和边界。
- 不要把会改变方案结构的需求问题延期到方案阶段。
