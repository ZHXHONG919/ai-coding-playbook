# 需求确认阶段

> 目标：把需求分析阶段的多轮共识冻结成进入方案设计的需求基线。复杂需求没有完成需求确认，不进入方案设计。

## 定位

需求确认不是完整 PRD，也不是技术方案。它只回答：

- 哪些需求已经确认，可以作为方案依据。
- 哪些只是 AI 推断，不能写成事实。
- 哪些仍未确认，会影响方案方向。
- 文档里是否还有互相冲突的口径。

需求阶段提出的问题，必须在需求阶段处理。方案阶段只能基于已确认需求做论证、建模、取舍和工程设计，不能把需求边界问题延期到方案阶段解决。

本节确认门禁面向开工前。需求/原型已确认并获实施授权后，不因执行中出现缺口自动重开本阶段的问答；主线程按 `references/delivery/agent-delivery-flow.md` 的自主推进约定查事实、作范围内决定并留证，用户主动介入时再同步方向。Agent 决策保留自身来源，不伪装成 Confirmed 用户口径。

## 触发

命中任一条件，进入方案设计前必须先做需求确认：

- 需求经历多轮讨论，已有 `requirements.md`、旧方案、历史对话或用户口头共识。
- 按 `references/stages/plan.md` 判断为复杂方案，且存在新的归属、核心状态、权限、最终消费方式或难以回退影响。技术名词、文件数和任务数本身不构成确认门槛。
- 用户明确说“先确认需求 / 先对齐口径 / 有问题先停下来确认 / 不要把需求问题拖到方案阶段”。

普通小改可以轻量确认，例如一句话列出范围和非目标；不需要生成完整确认稿。

## 工作方式

1. 读取目标项目事实、历史方案、已有需求稿和相关对话摘要。
2. 抽取已确认结论、反需求、待确认问题和 AI 推断。
3. 检查需求稿内部冲突，例如同一原型既说“不落代码”又说“可点击实现”。
4. 先查能从项目事实回答的问题，再判断未知项影响。会改变方向或后续大量依赖的先收口；可局部替换且不改变验收的默认值记录依据后继续。
5. 在 `requirements.md` 维护当前业务决策，其他文档引用。会话已有充分证据和用户授权时直接记录通过；需要新产品决定时只暂停依赖部分，不重复询问已明确结论。

## 高影响未知项优先

按本轮相关性判断，不逐项盘问所有项目：

- **所有权与消费者**：平台共享、商家私有、用户私有或任务快照；谁维护、谁最终使用。
- **成功含义**：保存、预览、发布、执行和下游消费分别完成了什么，本轮要交付到哪一步。
- **人工与自动**：哪些值可建议，哪些必须用户确认；代码在哪里强制边界。
- **状态与次数**：哪些入口可重试、恢复、终止或计次，是否共用同一业务规则。
- **当前环境**：是否已经上线，真实旧数据和旧写入者是否存在；不以“将来可能有”制造本轮兼容任务。
- **外部能力**：关键能力能否使用、最早在哪个功能批次通过实际路径验证；权限不足如实记录。

高影响 `Assumed` 必须在依赖实现前取得事实或用户决定，不能只贴一个标签后照常构建整条流程。低影响未知项写默认值及最晚验证点即可。

## 需求确认基线

复杂需求的 `requirements.md` 必须有明确的需求确认基线，不能只用散落段落表达“已确认 / 待确认”。推荐格式：

| 分类 | 内容 | 影响 | 处理规则 |
| --- | --- | --- | --- |
| Confirmed | 用户已确认的目标、当前有效业务规范，或用户认可需保留的既有行为 | 可作为 `plan.md` 的方案依据 | 标明来源；方案阶段做论证、建模和工程映射 |
| Pending Blocking | 不确认会改变领域抽象、字段归属、状态流、接口或任务拆解的问题 | 阻塞方案细节 | 不进入表设计、API、状态机、任务拆解 |
| Pending Non-blocking | 不影响主结构的参数或实现细节 | 可进入方案，但要记录默认值和回退 | 放入方案的“实现前确认”或风险 |
| Assumed | AI 基于证据做出的推断 | 按影响决定是否阻塞 | 标明证据、验证点；高影响项在依赖前收口 |
| No Longer Re-ask | 已足够明确、后续不再反复问用户的共识 | 降低多轮噪音 | 方案引用即可，不重新发散 |

如果需求稿中仍存在 `Pending Blocking`，方案阶段只能输出候选方向和待确认问题，不能把它改写成已确认决策。

区分“已核实的现状”和“认可的目标”：源码、旧测试、实际接口可以证明现在怎么做，不能单独证明应该继续这样做。现状与有效业务规则冲突时，写清两者来源和影响；不以旧测试通过把现状升级为 `Confirmed` 目标。用户已明确要求保留的旧行为是有效回归基线，不因来源标注再加一次固定确认。

## 文件落点

需要独立需求确认稿的复杂需求，将需求和方案放在项目已有 feature 目录，例如：

```text
docs/features/YYYYMMDD-short-topic/
  requirements.md
  plan.md
```

- `requirements.md` 保存需求分析和需求确认基线。
- `plan.md` 必须基于同目录 `requirements.md` 编写，并在开头引用需求基线。
- 如果业务项目已有本地目录规范，可以沿用，但必须保证 `plan.md` 能反向追溯到需求确认稿。
- 复杂需求没有 `requirements.md` 或等价需求确认记录，不进入 `plan.md` 的领域抽象、表设计、API、状态机或任务拆解。
- 少量步骤、讨论与验证可写在现有文件中；是否增加 `tasks.md`、`notes.md` 或 Goal 包按实际需要选择，不因落盘自动创建。

## 输出至少包含

| 部分 | 要求 |
| --- | --- |
| 已确认需求口径 | 有用户决定或有效业务规范作为依据，并与仅观察到的实现现状区分 |
| 非目标 / 反需求 | 明确本轮不做什么，尤其是容易误入的实现方向 |
| 关键产物与消费者 | 输入、输出、审核对象、下游消费方 |
| 状态与生命周期 | 有状态、审核、晋升、失效、重算时必须说明 |
| 复杂链路边界 | 异步、LLM、外部 provider、同步、权限、发布等边界 |
| 页面流 / 审核对象草图 | 涉及后台、运营、审核、批量操作时，说明用户看什么、审什么、在哪里通过/打回/编辑 |
| 待确认阻塞项 | 不确认会改变方案结构、表设计、接口或任务拆解的问题 |
| 一致性检查 | 需求文档中互相冲突、过时或重复确认的内容 |

## 通过标准

进入方案设计前必须满足：

- 关键业务目标、范围、非目标和验收口径已明确。
- 涉及后台、运营或审核流程时，页面流和审核对象已清楚；如果不清楚，不能进入复杂方案细节。
- 会影响工程结构的需求决策已经收口，例如数据写入时机、审核对象、产物契约、同步边界、模型输出可信口径。
- 剩余待确认项不影响方案主结构；若影响，继续停留在需求确认阶段。
- 已明确哪些内容是 `Confirmed`、`Pending`、`Assumed`。
- 没有 `Pending Blocking` 被方案、数据模型、API 或任务拆解当成已确认事实。
- 当前有效规则和引用无冲突；历史报告保留当时事实并标明已被哪项新决策替代，不反复改写历史。

## 禁止

- 不要把需求确认写成表设计、API 设计或任务拆解。
- 不要用“方案阶段再分析”掩盖尚未确认的需求边界。
- 不要把用户未确认的 AI 建议写成已确认结论。
- 不要把 `Pending Blocking` 直接转写成关键决策、字段、API 或任务。
- 不要反复询问已经确认的共识；应该记录到“不再重复确认”或等价章节。
