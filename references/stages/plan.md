# 方案设计阶段

> 技术方案服务于后续任务拆解、实现与验收。完成标准是实现者能据此落实用户结果、验证关键规则，而不只是文档写完。方案阶段默认不改业务代码。

## 先确定本轮在做什么

结合用户最新请求、项目事实和当前方案判断工作方式；对话从局部评审转为完整设计时重新判断，不能继续沿旧稿追加补充段落。

| 本轮工作 | 采用方式 | 结束时交付什么 |
| --- | --- | --- |
| 新写完整方案 | 按下文完整编写流程 | 贯通的八章设计及实施交接，未定条件影响范围清楚 |
| 整体重构已有方案 | 旧稿是证据输入，重新执行完整编写；保留有效结论和已确认原型 | 重组后的当前方案，不维护两套规则，也不以追加补丁代替重构 |
| 局部讨论或设计评审 | 读当前方案和受影响规则，用 design-review 检查相关范围 | 当前问题、证据、裁决和影响；不机械输出八章或重排全稿 |
| 局部行为、成熟契约复用的小改 | 按下文统一准备取得轻量方法，再按方法取得项目定义 | 简短方案及必要验证，不因落盘或涉及API自动升级 |

改变共享权限、身份、计费、核心状态、不可逆数据或出现决定可行性的未知时，对受影响部分做详细设计。用户明确要求完整方案时按请求展开。只是接触多个文件、数据库或前端，不决定复杂度。局部评审发现需重建核心模型时说明原因；用户已要求整体重构，直接进入完整编写，不反复询问。

## 统一准备，再取得项目定义

入口已取得项目README、AGENTS、CLAUDE中存在文件的正文后，按其约定确定规则根，并结合用户请求和项目概要选择完整或轻量方式；不先细读契约来填方案。本地明确指定根优先，不混读全局旧模板。可在选定根执行一次方法准备，完整用full，轻量用light；已有文件工具等价取得同一组正文也成立：

```sh
python3 <选定根>/scripts/read-plan-context.py method --root <选定根> --mode <full或light>
```

该动作返回选定根AGENTS、本阶段和适用方法的实际全文：full为编写规范、证据方法、角色视角及正式模板；light为兼容入口、轻量编写规范、证据方法及轻量模板。给读取工具足够输出额度，确认整组正文实际完整返回，再按所读方法发现相关模块及读取具体定义；准备与依赖它的细读不并发。报错读取中已实际返回的正确文件可保留，缺失方法仍须补齐，不能把整条命令退出状态当作每个文件是否取得的证明。包或单文件被截断时按返回清单逐文件、逐连续行补齐，例如：

```sh
python3 <选定根>/scripts/read-plan-context.py method --root <选定根> --mode full --file references/plan/plan-writing-guide.md --start-line 1 --end-line 80
```

按返回的total_lines继续后续连续范围；原生文件工具也可按明确路径和连续区间返回正文。全文版本一致且覆盖完整后才继续，不能用摘要、哈希或结束码代替正文。已有同版完整准备返回可复用，不每次局部修改重读。项目约定与其明确选定根的准备规则可在一次有明确先后、无并发的读取中依次取得；详细定义须等整套方法实际完整返回后再开始。两种读取方式使用同一依赖顺序，不安装工具或新增台账。

范围不清时可先读用于判断需求范围的概要，取得相应方法后再追具体定义；后来发现范围需扩大，先补齐相应方法再继续依赖它的设计。准备流程只在本处定义，轻量及完整编写共用。

## 进入完整编写

1. **采用准备好的方法与骨架。** 完成上述full准备后，规范负责推导和表达，证据方法负责发现资料，模板负责呈现，不另开一条预读流程。
2. **取得并采用输入。** 按已加载的证据方法发现相关模块，再读取需求采用稿和实际定义，确定参与者、入口、必要读取、相关既有行为与消费者，未知明确边界。复杂需求没有确认基线时读取 references/stages/requirement-confirmation.md；已有确认不重复提问。界面采用已有 ui-flow.md / prototype，不凭想象替换导航。
3. **补必要专项。** 新概念/归属、状态图、技术栈、迁移、异步或外部依赖，仅按本次风险选相关 references/plan/*、references/scenarios/*。专项承接项目风险，不再组合第二套章节目录。
4. **按规范形成定义并在八章成文。** 依编写规范先确定动作结果与查询含义，再归纳共同职责和所属完整属性/关系定义，与存储/API共同落实；图及少量实例采用同一结论。方法只在规范维护，本阶段不再生成第二套算法。定义直接放入模板负责位置，完整已有内容精确引用；重构将有效结论放回所属章节，不沿旧稿加补丁。普通讨论只答当前问题，不执行全套成文。

正式方案采用的需求、交互和规范版本在已有文档头部或来源说明中简记。目的在于后续使用同一依据，不新增读取回执文件，也不能用“我已读过”代替产物符合规则。

## 作者怎样检查采用结果

完整方案交付草案前，按 references/plan/plan-writing-guide.md 的“从草案到采用稿”完成标准自检。该处统一检查行为、共同模型和存储/API是否成立，以及各章产物能否供接手者使用；本阶段不另列第二套检查单。按实际完成情况交付草案或采用稿，明确局部缺口和证据边界。

方案末尾给实施与验收交接：主要用户结果及依赖、代表输入和最早真实路径、需尽早证实的判断、仍模拟或未验证的能力、设计评审状态和未闭合条件。已有材料直接引用，没有独立任务稿时在此简述，不为引用先造整包文档。

## 独立设计评审与移交

完整方案可以先交付可评审草案。进入正式任务拆解或实现前，由独立Reviewer按 skills/design-review/SKILL.md 读取同一采用版本及规范评审；当前主线程判断证据前提与范围，采纳、拒绝或安排局部处理，不能把严重度标签直接当业务决定。没有独立能力时明确自审和限制，不虚报独立审查。

评审沿用编写规范同一完成标准，检查设计关系与产物可用性，不能只审业务逻辑而漏掉交接所需的图和协议。发现问题修正当前来源和实际受影响设计，复核对应范围；不因一次反馈重审整个方案。章节齐全本身不构成Ready。

交接到 references/plan/task-breakdown.md：任务拆解是设计转执行的正式节点，按 templates/tasks/ 形成具体领域能力及用例功能文档；方案第3至6章提供行为、职责、存储和协议，不在任务中重新设计。界面任务精确承接采用原型和固定图片，完成标准由任务拆解规则定义；不为交接提前生成整包任务。交付按用户结果组织，服务端按共同领域能力及依赖展开，不能按八章各拆一个任务。近期工程步骤消费已采用契约、前提和验证标准；高影响未知在依赖前核实，其余局部细节滚动补齐。复杂方案CR复用已有有效结论，Goal仅在需要结构化恢复或用户明确要求时采用。

## 授权与文档边界

- 用户说“写方案、先讨论、先别写代码”时，停在方案；只有明确实施授权才进入编码。目的服务落地不意味着自动实施。
- 只在聊天讨论，不要求切分支或建文件。要求落盘时按 references/stages/feature-kickoff.md 的 doc-write gate 和 references/git-safety.md 检查分支，plan.md与需求稿放项目约定位置；保存轻量方案不升级全套。
- 用户最新确认的业务规则优先于工程直觉，不以更保守、更安全或技术限制悄悄改变按钮、数量、人工边界。高影响口径冲突只阻塞依赖部分，不能任选一种实现。
- 新的主用户路径需要确认，已有确认基线及后续授权直接复用。涉及后台、审核、批量等界面，已有UI Flow/等价路径用于设计，不重复生成原型或停顿。
- Open Design按 references/scenarios/open-design.md 判断；局部字段、按钮、文案、间距不默认使用。目标项目已安装 impeccable 时按本次原型变化选择检查，已有有效结论复用。

## 最新要求与一致性

业务决定只在需求基线定义，方案引用决定及必要原文；领域与工程选择按 references/plan/decision-table.md 记录和同步。用户明确变更先更新唯一来源，再沿负责能力、存储、协议及验证找到受影响部分；未变内容复用，历史报告标为被替代即可。不得把新建议写成已确认规则，也不逐份复制另一张业务规则表。
