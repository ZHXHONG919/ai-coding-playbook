# 证据驱动交付

> 围绕已确认行为选择最小充分证据。每个结论都说明观察到了什么、能证明什么；普通任务共享结果证据，不重复搭环境、写报告或截图。Goal 统一以结果为验收单位。

## 从行为选择证据

正常开发以有效需求、用户认可的既有行为或已确认界面为基线；修复以问题原始来源和复现结果为依据。先按 `skills/test-scope-analysis/SKILL.md` 写检查单：

```text
改变的行为 → 关键反例 / 风险 → 真实入口与观测点 → 预期结果 → 足够的证据
```

“必要自测”由这份检查单决定，不是固定执行 lint、typecheck、build、全量 test 的组合。实现者执行任务自测；关键基础及完整结果需要独立判断，审查安排统一遵循 `references/stages/review.md`。

## 观测生产行为，保持期望独立

- **实际入口：** 选能覆盖本次行为的生产函数、服务接口或客户端入口。跨模块验收尽早接通一条最短应用路径，不用多组互不相连的单测推断整体已跑通。
- **实际结果：** 响应、状态、调用次数、因果关系和存储内容必须从运行结果读取。将预期常量写进报告、读取上游状态代替最终状态，均不能证明最终行为。
- **独立期望：** 来自有效业务规则、按该规则确定的冻结样例或用户认可的既有行为；只观察到旧代码/测试如此，不自动成为验收口径。来源冲突先说明，选一个能区分最可能两种解释的输入，不用旧测试通过决定产品口径。禁止用本次实现计算期望值，再以相同计算证明自己正确；基线变化需解释原因，不能直接更新快照吞掉差异。
- **替身边界：** 可替换数据库连接、时钟、provider 等外部依赖，但保留被测业务判断。固定 provider 只校验真实请求并返回预声明响应，不在替身内重写路由、质量判定或回退决策。
- **真实写后读：** 被测代码执行写入，再从同一个存储读取；手工预填“最终记录”只证明读取功能。使用内存存储时说明与真实数据库的差距，事务/锁/约束本身的验收需要相应数据库证据。
- **能检出错误：** 高风险验收挑一个相关错误输入、断开调用或字段篡改，确认检查会失败。无需为所有任务另建完整变异测试体系。
- **识别假接入：** 新增服务端 Mock 的当前路径，选一个能区分“消费响应”与“前端自造结果”的样例。例如改变服务端候选值，观察页面实际变化；涉及保存时通过正常页面保存并重开读回，再验证一次保存失败不会显示成功，只读场景不为此新增保存操作。使用项目已有请求层与观测方式，不为此建设通用探针或完整模拟数据库。HTTP 200、请求日志和特征值均只作辅助，不能单独证明页面消费了响应；成熟真实接口的无关样式修改不强制加入这项检查。
- **模型质量边界：** 固定模型响应能证明应用如何构造输入、消费输出与保存结果，不能证明真实模型效果。若验收要求实际生成质量，应单独安排已授权环境的代表性评测，写明配置、结果和波动，不能用 mock 通过替代。

## 证据等级

| 等级 | 适用范围 | 最小充分证据 |
| --- | --- | --- |
| E0 | 重复问题、非问题、口径误解、无需运行的文档变化 | 产品口径、位置、历史提交或重复关系 |
| E1 | 后端逻辑、接口、状态、数据、历史已修复 | 针对性测试、真实接口响应、数据读回或当前路径检查 |
| E2 | 页面功能、入口、权限、状态展示 | 浏览器或客户端操作验证；必要时保留关键截图 |
| E3 | 视觉差异、复杂交互、多角色、多端一致性、真实环境问题 | 基线/实现对比、关键角色和端的同路径证据 |

等级只选择证明手段，不决定审查轮数，也不代表越高越好：

- 用户可见界面行为至少需要运行态检查；视觉、跨角色或跨端结论要有对应对比。
- 并发、事务、权限、幂等和数据正确性不能用截图替代行为证据。
- 历史已修复问题要求当前路径证据，不强制重建修改前现场。
- 多个任务共用同一路径、角色和状态时共享证据，并指明各自证明的行为。
- 无法取得必要证据时标明未验收部分及影响；仍可推进无依赖工作，不把缺口写成通过。

## 界面验证与预算

涉及界面的任务声明界面基线、需要证明的关键状态及证据门禁；无界面变化可写 `界面基线：无`、`证据门禁：接口/数据证据`。

### 图片、交互原型与业务约定各自负责什么

有已确认界面的实现与验收，按下面的分工选择依据；三者共同约束同一功能，不能用某一类通过代替另外两类。

按原型还原时，图片基准贯穿三个阶段，职责不能后移给实现者：

| 阶段 | 负责动作 | 交接与检查 |
| --- | --- | --- |
| 原型准备与采用 | 原型准备方在开发前准备关键状态图片，打开保存原图核对，再随原型确认采用版本 | 在现有ui-flow或原型说明关联采用版本、图片路径、端/角色/状态及比较条件；已有同版确认复用 |
| 开发与恢复 | 实现者实际打开已采用图片，按图落实画面，并按原型/业务约定接交互与数据 | 引用同一基准；缺图、错图、版本不符回原型准备环节，不能自行截图建立或替换基准 |
| 验收与修复复核 | 验证者核实仍是原采用图片，打开同条件的实际页面和保存截图逐项对照 | 记录参考图版本/位置、实现版本/状态、实际证据与差异；检查遗漏和擅自新增，不把实现截图或更新后的实现快照当参考图 |

实际页面截图与原型参考图片分开保存或明确标识，避免同名覆盖。需要修订基准时回到原型采用环节，保留旧版本及新的采用依据，再使受影响对照结论失效；不是由实现者或验收脚本更新快照来自动接受差异。不新增独立审批表或强制文件格式，沿用下文的现有来源记录。

| 依据 | 负责决定 | 实现与验收方式 |
| --- | --- | --- |
| 已确认原型的关键状态图片 | 该状态的布局、字号层级、间距、密度、颜色、按钮原文与位置 | 实现前打开实际图片，按可复用结构和样式还原；运行后在相同内容区域、视口、缩放、字体条件及代表数据下对照，分别说明差异 |
| 可操作原型及页面流程 | 入口、动作顺序、展开/选择/关闭、禁用条件的交互表现、反馈与返回 | 实际操作原型及产品；图片只是瞬间，不能推断点击后跳转、是否已调用识别、返回保留或其他隐藏状态 |
| 已确认需求及接口/状态约定 | 数据来源、权限、业务状态、请求触发时机、校验、保存、恢复与失败处理 | 使用正常应用入口和请求层观测请求与读写结果；不把原型的固定演示数据、浏览器存储和伪业务逻辑搬进产品 |

关键状态图片由原型准备方在相应界面开发前维护，作为采用稿的一部分交接，不留给实现者边开发边截取和选择。图片从当前采用原型的真实运行页面截取，复用已有合格图片；按本组实际风险选默认态、打开后状态、确认/授权、失败和结果，不要求每个任务全套截图。在已有 ui-flow、原型说明或任务记录维护同一处图片对应：来源版本/区块、端与角色、状态、到达步骤、浏览器视口与目标内容区尺寸、滚动位置及图片路径。截图前完成相应操作，必要时用顶部/底部多图，保留上下文和可读控件；保存后必须打开检查，不使用加载中或截断关键结果的画面。原型外框、调试栏与产品内容区分开标明，不为凑一张图缩小文字，不修改原型CSS制造参考图。

原型准备方核对实际保存的图片与页面状态、文案、控件和来源是否一致，并在原型采用时一并确认图片版本；已有同版确认直接复用，不增加逐张审批。交接后保留这版图片的稳定路径和版本，后续变更另留新版本及采用依据，不覆盖旧图。实现者自己的截图用于观察实际结果，不成为参考基准，也不能根据实现效果重截原型、替换参考图来消除差异。原型准备与实现由同一Agent承担时也按先后分开：先完成图片检查与采用，再开发，不能边写页面边自行改基准。

截图是采用稿的可视补充，不是独立的一份业务决定。先核实图片与可操作原型来自同一有效版本/状态；旧图不能覆盖新确认，图片不能证明其没画出的权限、请求或返回行为。出现冲突时按用户最新决定及该区块有效来源判断：能从已有确认确定就修正过时材料；无法确定才暂停受影响部分并说明具体冲突，不自行择一，也不重问已确认规则。

派发按原型还原的界面实现时，须同时引用已采用的关键状态图片、可操作入口和业务约定，执行者需实际查看图片，不能只读文件名或源码。缺图、图截错状态或与采用版本不符时，交回原型准备环节补齐、核对并更新采用依据；实现者不能用自行截取的候选图解除缺口，受影响界面先不按猜测开发，无依赖工作可继续。已经实际查看采用状态并有足够视觉输入的普通小改，不为形式补整套图片，也不授权改写既有基准。缺失关键视觉输入时写明缺口，不能以业务测试绿宣称还原通过。实现优先复用原型结构、样式和现有组件，不能仅凭图片臆造交互或将原型HTML整页嵌入正式产品。

**每个区块或动作的同一维度只用一个当前依据。** 用户的新决定可能只覆盖卡片结构，旧系统样式仍有效；不能按整份文件新旧排序，把较早原型重新覆盖已认可的局部改动。v3 在结果的 sources / decisions 引用当前依据及区块，引用变更进入结果核验；已有 ui-flow 索引直接复用，不新建强制交接报告。任务只规定实现范围，不得改写这里的动作含义。

对照必须双向进行：既检查采用稿的区块与动作是否落实，也检查实际页面新增、删去、移动或默认展开了什么。服务端返回了字段、组件方便复用、实现者认为“信息更完整”，都不是改变页面内容和摆放位置的依据。沿用现有记录，为有意义的差异注明当前来源或已授权例外；已有业务约定只要求保存或可查时，不推导为成功页默认展示全部材料。反过来，最新业务决定明确要求的提示不能只因旧图没有而删除。能按已有决定裁决就直接处理，只有真实冲突才澄清。

```text
UI-01：当前结果 <R-xx / revision>；采用稿 <路径/预览入口及可定位版本和区块>；确认依据 <已有用户决定>。
分工：<该来源决定哪些结构/动作；其他仍有效来源负责哪些样式/规则；被新决定替代的旧约定不再参与裁决>。
范围与比较条件：<页面/区块、状态、参考视口、代表性数据>。
保留项：<布局、字号层级/密度、关键控件；操作/反馈/跳转；业务契约编号>。
允许差异：<已授权的文案删除、真实数据替换、响应式适配等具体范围；未授权部分保留采用稿>。
```

实现者与修复者先实际打开采用稿及相关结构/样式。优先迁移可用结构、样式和组件再接真实数据；框架转换、组件库默认值或通用 polish 建议不能覆盖确认效果。只有源码而无法查看预览时，说明视觉输入缺口，不能把读源码当成运行对照。

新页面、大改版或共享视觉基础首次可运行时，以同视口、代表性数据对照一个页面的当前这一态，先看主要布局、层级和关键控件。把这次结果放在现有自测记录，指出采用稿、实现版本、比较条件及有意义的差异；不新增 CR 批次，不要求每个任务截图。这一态通过只证明该态。本组体验门禁通过前，不把该布局用到其他页。无法对照时保留校准缺口，推进无依赖工作，不能把同一未验证布局扩散后再统一返工。

画面还原可在真实页面首次可达时先检查，不等待上传、审核或跨端流程全部跑完。检查的是当前真实页面，不手造最终业务记录来冒充流程通过。先确认同一产品内容区、页签、角色、业务状态和代表数据；窗口宽度、原型外围导航、测试文案长短或空列表造成的差别先排除。对照条件不齐时只报告已能判断的部分，不把不同页签、不同对象或空态与有数据态直接判成还原缺陷。视觉检查不替代后续已承诺的交互和业务验收，也不扩大本次用户只要求的试看或对比范围。

界面批次分别给出以下结论，比较原型不能只比较像素：

| 维度 | 要证明的结果 | 对应证据 |
| --- | --- | --- |
| 视觉还原 | 确认的布局、层级、密度与关键控件保持一致，差异在授权范围内 | 同视口/状态的关键图片或已实际打开的采用稿与页面对照；必要时查计算样式，不默认要求所有页面逐像素一致 |
| 交互一致 | 主路径、入口、操作条件、反馈和跳转符合确认流程 | 实际点击/键盘操作与关键状态验证，截图不能单独证明 |
| 业务正确 | 数据范围、单位、权限、状态与接口结果正确 | 实际应用路径及必要读写/权限证据，视觉相似不能代替 |

视觉未验证时写“还原待验收”，不能以源码 `Fixed`、测试绿或用户将自行验证推导整体完成。用户主动要求手动验收时提供采用稿、当前页面及待验关键项，收到实际结果后再更新对应结论，不重复索要已给予的授权。本组体验门禁通过前，还原待验收不能用来进入真实后端或复用布局，也不能把尚未操作的状态交给用户补。

本组界面在进入真实后端或复用布局前，还要满足 `references/stages/review.md` 的前端体验门禁。采用稿里已经画出的状态，以及点开之后才出现的状态，都要实际操作；展开、选择、关闭、返回只是例子，不是全部。默认静止画面只证明默认态。现有记录里每个动作写下点完之后页面变了什么，以及哪条请求是这次点击引起的。只有「已到达 / 一致 / 已操作」、实现者事先列的名单，或子代理回传的「已对照」，都不移动下一步。不另建原型要求文档，但必须按 `references/stages/review.md` 的“前端体验放行前的覆盖核对”将采用稿与现有操作证据对应；没有请求的动作明确记无请求，不能只留成功终点。

- 同一页面和批次集中验证，普通任务先做轻量实际查看，不反复制作最终截图。
- 保留能证明主路径、最高风险异常/权限状态和关键成功结果的材料；已经点过并记下变化的状态可以复用自动化覆盖，无需每个状态留图。还没点过的状态不能用自动化或读源码填上。
- 最终证据与代码审查可在同一固定版本并行完成，合并写入批次验收记录；不强制另建逐片 `evidence-confirmation` 报告。
- 修复改变了哪些行为或呈现，就重查哪些状态；未受影响证据可复用。纯报告变更核对事实即可。
- 客户端控制连续同类失败时，依据错误换定位或采集方式；不要无限重试。更换手段不能降低原证明目标，接口/数据不能替代视觉结论。浏览器或预览打不开时，视觉和交互写入现有缺口，本组不进入真实后端，布局不接到其他页；读源码和请用户逐页对照都不能解除。必要登录仍登记缺口，不把未操作的状态写成通过。

## 固定版本，集中验证

```text
确认行为与检查单
→ 尽早接通最短应用路径
→ 普通任务连续实现与自测；关键基础在依赖前审
→ 相关结果构成完整使用过程，按 review.md 合批固定代码及约定版本
→ 独立验证者从当前来源写预期和判错数据，先运行，再读实现报告并 CR
→ 主线程裁决问题，集中修复
→ 原失败路径和影响范围复验 / 复审
→ 交付版本增量覆盖检查
```

独立验证前可以读取启动命令、数据准备和版本等中性事实，不先接收“已经通过”的实现结论。每条证据记录代码版本和相关配置；外部环境变化也要说明。固定版本期间不改同一范围，独立范围工作可继续；必须修改时重新标定版本，仅使受影响结论失效。

全量回归不是 Goal、批量问题或最终收尾的固定动作。共享规则影响面无法可靠隔离、项目明确要求或交付风险需要时运行；可信的已通过检查可复用，不因进入另一审查环节再跑一遍。修复影响域与同类问题根因分析见 `references/stages/review.md`。

## 问题来源与批量处理

从会话、工单、截图、录屏、日志、监控、失败测试、CR 或数据收敛必要信息，可记录在现有任务台账：

```yaml
source:
  type: conversation | ticket | screenshot | recording | log | test | monitoring | review | data
```

## 输出

普通任务合并记录改变的行为、自测结果及缺口，不强制另写报告。正式核验记录：

- 基线、代码版本、配置与实际入口。
- 关键预期、运行观测、证据位置及充分性。
- CR 发现的主线程裁决、修复和影响范围复验。
- 尚未覆盖的行为、原因、负责人与交付影响。

记录帮助恢复和核验，不追求报告数量；测试绿、审查通过和交付完成分别陈述。
