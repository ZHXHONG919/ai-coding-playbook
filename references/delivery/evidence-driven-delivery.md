# 证据驱动交付

> 目标：让需求开发和问题修复都围绕“期望基线 → 当前结果 → 差异 → 修改 → 同路径验证”形成可检查闭环，同时按风险选择最小充分证据，避免所有任务都走截图、真实账号和全量回归的最重路径。

## 适用范围

- 正常业务开发：需求、界面流程、原型或设计稿已经形成期望基线，需要验证实现是否忠实落地。
- 问题修复：问题来自对话、工单、截图、录屏、日志、监控、测试失败、代码审查或线上数据，需要统一受理、分类、复现和验证。
- 批量问题：多个问题来自同一来源或多个来源，需要按父子关系、用户路径和共享根因聚类处理。

本规则不绑定飞书、GitHub、Jira、Linear 或任何具体平台。外部平台只负责提供输入和接收可选的状态回写。

## 通用闭环

```text
期望基线
→ 当前可观察结果
→ 差异与影响范围
→ 最小修改
→ 同路径验证
→ 相邻路径回归
→ 证据与结论
```

正常开发的期望基线可以是已确认需求、`ui-flow.md`、静态原型、Figma、Open Design 产物或现有页面。问题修复的期望基线可以是产品规则、历史正确行为、接口契约、测试断言或用户确认口径。

## 问题来源归一化

无论问题来自哪里，先整理为统一的问题受理信息：

```yaml
source:
  type: conversation | ticket | screenshot | recording | log | test | monitoring | review | data
  reference: "<原始消息、链接、文件、日志或编号>"
symptom:
  observed: "<实际发生了什么>"
  expected: "<期望是什么；未知时标记待确认>"
  environment: local | test | production | unknown
  affected_surface: web | miniprogram | api | job | data | multi_client
reproduction:
  steps: []
  role: "<用户或系统角色>"
  test_data: "<必要测试数据>"
  reproducible: yes | no | partial | unknown
scope:
  parent_case: null
  child_cases: []
  related_cases: []
evidence:
  level: E0 | E1 | E2 | E3
  available: []
  missing: []
```

- 来源不支持状态回写时，直接在任务记录和最终回复中闭环。
- 来源支持状态、负责人、备注或附件回写时，才增加写回；写回后必须读回确认。
- 批量问题必须在开工前展开父记录、子记录和关联记录，冻结数量与状态分布，不能只处理列表第一层。

## 证据等级

| 等级 | 适用范围 | 最小充分证据 |
| --- | --- | --- |
| E0 | 重复问题、非问题、口径误解、无需运行验证的文档问题 | 产品口径、代码位置、历史提交或重复关系 |
| E1 | 后端逻辑、接口、数据状态、历史已修复 | 聚焦测试、接口响应、数据读回或当前路径验证 |
| E2 | 页面功能、入口、权限、状态展示 | 浏览器或客户端冒烟验证；必要时保留关键截图 |
| E3 | 视觉差异、复杂交互、多角色、多端一致性、真实环境问题 | 修改前后或基线/实现对比、关键角色与关键端证据、同路径验证 |

规则：

- 每个任务都要有证据，但不是每个任务都要截图。
- 用户可见的界面问题默认至少 E2；视觉、跨角色或跨端问题默认 E3。
- 后端、并发、事务、幂等和数据正确性问题不得用截图替代测试、接口或数据证据。
- 历史已修复问题只要求当前路径证据，不强制重新制造“修改前”现场。
- 多个任务共用同一页面、角色和状态时允许共享证据，但必须逐条说明证据证明了什么。

## 界面基线与证据门禁

涉及界面的任务在 `tasks.md` 中声明：

- `界面基线`：`无`、现有页面、`ui-flow.md`、静态原型、Figma、Open Design 产物或用户截图。
- `证据门禁`：`无需视觉证据`、`冒烟验证`、`实现截图`、`修改前后对比`、`原型对比`、`角色对比`、`多端一致性` 或 `接口/数据证据`。
- `关键状态`：只列必须留证的正常态、空态、错误态、权限态、冲突态或成功态。

原型或设计稿对比不能只做像素比较，至少检查：

1. 主用户路径和入口。
2. 操作矩阵、可用条件与危险操作确认。
3. 角色、权限和状态映射。
4. 加载、空、错误、权限、冲突和成功状态。
5. 信息层级、响应式、溢出、可访问性和设计系统一致性。

纯后端、脚本、任务、迁移或无界面变化的改动，应明确写 `界面基线：无`、`证据门禁：接口/数据证据`，不要为了形式截图。

## 证据预算与执行时机

- 一个页面默认只保留一个正常主路径、一个最高风险异常/权限状态、一个关键操作成功结果；其他状态优先由自动化测试覆盖。
- 多个实现任务共用同一页面时，合并为一个 `QA` 或 `INTEGRATION` 验收任务集中截图和比较。
- 实现后先跑聚焦测试，并在首轮代码审查前做一次轻量界面检查，只确认主路径可达、基线可读取、没有明显契约偏差；首轮代码审查的阻塞修复完成、准备复审前，再制作最终截图、原型对比等视觉证据，由复审同时确认修复和证据。
- 首轮代码审查如果没有阻塞问题，立即制作最终证据，优先由原审查者做限定范围的证据确认；原审查者跨会话不可恢复时，由同职责且独立于实现者的审查者接替并记录原因。Goal 场景写入 `.goal/cr/<slice>-evidence-confirmation-<n>.md`。
- 最终证据确认必须比较当前代码与关联代码审查输入。关联审查后只要运行时代码发生变化，就必须重新做限定范围代码审查，再更新最终证据；只有证据文件和报告变化时才允许直接做证据确认。
- 最终全量回归不是所有任务的固定动作。Goal、批量问题、共享核心/契约/基础设施或高风险改动在交付收尾运行一次；普通局部改动只跑受影响测试和相邻路径，并记录不跑全量的理由。共享核心再次变化时才增加全量回归。
- 同一界面自动化控制最多尝试两种稳定定位方式，每种方式最多两次完整尝试；连续两次同类失败立即降级。降级只能更换采集手段，不能降低证据等级或跳过原证明目标：E2/E3 问题仍需等价的运行态或视觉证据，接口与数据只能补充、不能替代视觉结论；无法取得等价证据时登记人工介入或阻塞。不得在同一种方式内无限重试。

推荐顺序：

```text
确认基线 / 保存必要的修改前证据
→ 实现
→ 聚焦测试
→ 轻量界面检查
→ 首轮代码审查
→ 完成阻塞修复并重跑受影响验证
→ 最终界面证据 / 原型对比
→ 复审同时确认修复和证据
→ 按风险决定交付收尾全量回归
```

## 批量问题提速

批量问题按用户路径和共享根因聚类，而不是按工单逐条重复启动环境：

```text
展开父子问题并冻结台账
→ 按页面 / 角色 / 接口 / 根因聚类
→ 一次复现同组问题
→ 集中实现共享修复
→ 聚焦测试与首轮代码审查
→ 一次验证同组问题
→ 批量写回并批量读回
```

- 一个开发切片只处理一个主要用户路径或一个共享根因簇。
- 不同问题共享证据不等于共享结论；每条问题仍要单独记录分类、影响、修改和验证结果。
- 非问题、历史已修复和当前确认问题应走不同路径，不得统一进入代码修改。

## 输出要求

每个任务或问题至少记录：

- 期望基线。
- 当前结果或修改前证据。
- 证据等级和选择理由。
- 修改范围。
- 同路径验证结果。
- 相邻路径回归范围。
- 未覆盖风险或人工介入项。
