# 用执行证据改进工作流

## 何时记录、记录在哪里

用户要求分析执行策略、试用新流程，或执行需要跨上下文恢复的 Goal 时使用。普通轻量修改可直接在现有实现记录或对话中留一行结果，不为留证升级成 Goal。

每个执行过程只保留一个索引：优先复用已有记录，没有时用 `.goal/execution-log.md`（非 Goal 可放在需求目录）。模板见 `templates/execution-log.md`。在任务完成、批次裁决、首次真实路径、返工、需求变化、阻塞或停止等已有边界追加；同一动作覆盖多个边界时合并一条。不记录每次工具调用，不另外维护一套任务状态，不要求新增日志服务。

## 最少留下什么

开头一次性记下任务范围/成功标准引用、流程版本、审查策略和开始时间。规则尚未提交时用内容快照或文件摘要，不只写分支名。模型、推理设置和上下文来源只有明确可得时才记录；未知写“未获取”。只记录传给执行者的约束来源和提示版本，不保存私密推理过程。

| 时点 | 需要留下的信息 | 可以回答的问题 |
| --- | --- | --- |
| 选择任务或并行方式 | 范围、实施者角色、为什么此时执行/等待/委派；引用任务卡与交接提示 | 批次是否过大？并行有没有等共享契约？约束是否传给实现者？ |
| 首次真实路径或代表页面校准 | 当时的代码/契约/原型版本、入口与观测、证据位置 | 集成或界面问题是不是发现太晚？ |
| 验证与 CR 完成 | 版本、覆盖范围、结果，引用原报告 | 检查是否有效？是否复查了无变化内容？ |
| 修复、返工或用户纠正 | finding ID / 问题族、当时有效要求、首次发现节点、影响与修复范围 | 是需求新变化、意图漏传、方案错误、实现缺陷，还是验证漏检？ |
| 局部隔离与回收 | 关联任务/缺口 ID、协议版本、为何可隔离、实际继续了什么、回收点与真实验证引用 | 隔离是否减少等待？是否把必需逻辑遗忘为 TODO？ |
| 等待与恢复 | 等待对象、开始/恢复时间（可得时）、恢复依据 | 时间主要花在执行还是等待？ |
| 交付 | 本次实际覆盖、未验证项、关键发现与下一次可试的小调整 | 质量与成本是否一起改善？ |

每条只写“时间 / 范围与执行者 / 动作及理由 / 实际结果 / 证据引用”。完整命令输出、截图、测试与审查内容只存一处。需要跨会话复查时，将必要的简短原始输出或裁剪证据保存到项目允许的位置；不要只依赖会过期的 `/tmp` 路径。沿用项目对业务数据和截图的存放约定，只保留最少的非敏感证据，不复制 token、密码、完整会话、用户数据或账号信息。

短任务默认一个事件表加几行归因/待试调整即可。同一事实不要在表格、归因、指标和收尾各复述一次；缺失数据合并一行，复杂判断引用原报告。只有确实影响结论的分歧才展开，不把本规则的解释逐条写入每次记录。

## 返工怎么归因

先记录可观察事实，再给原因；标明“已证实”或“待验证”，不能因后来某条规则能解释就认定是根因。

- 对照发生时已确认的要求。用户后来新增要求记“需求变化”，不能算成最初实现的缺陷；原要求明确但实现遗漏才是偏离。
- 区分首次引入与首次发现。定位不到引入节点就写未知；CR 发现问题不表示问题由 CR 造成。
- 发现规则没生效时检查关联、加载、读到、遵守的证据。主线程读过不证明 worker 读过；只有文件访问记录也不证明已理解。
- 同根因的多个 finding 合成一个问题族，关联受影响入口；已修复后同原因再次出现记再发。不同原因不要只因报错相似合并。
- 审查建议由主线程裁决为采纳缺陷、误报、后续建议或需求变化，保留简短依据。不要把全部 CR 评论都统计成代码缺陷。

## 指标只从证据计算

| 指标 | 口径与限制 |
| --- | --- |
| 首次真实路径耗时 | 同一次执行开始到首条真实路径成功证据的时间差；若没有开始时间，记未获取。界面校准单列，不混同业务集成。 |
| 总经过时间 / 等待时间 | 明确起止时间和是否跨用户暂停；并行子任务耗时不可相加冒充总经过时间。未完整记录等待时不推算“有效工作时间”。 |
| token | 只引用工具明确提供的本次执行用量与统计范围。主/子 Agent、缓存口径不清就注明不完整；账户剩余额度、文档长度、上下文大小不能替代本次用量。 |
| 重复验证 / CR | 同范围、同版本且无新依据的重复与修复后有必要的复验分开计数。不要把所有第二轮审查都当浪费。 |
| 返工 / 用户纠正 | 按已裁决的问题族统计，说明总量、发现节点及需求变化数量，不只给百分比。 |
| 交付后缺陷 | 给出观察窗口和反馈来源；尚未应用、没有后续观察不能写零缺陷。 |

数据缺失不阻止正常交付，也不能补写成零。旧记录回填须标“回溯”，附来源，不猜时间、用量或当时动机。原记录错误时追加更正，保留更正前依据，避免只留下整理后的成功故事。

## 怎样据此优化

先回答一个具体问题，例如“为什么同一页面返工三次”，沿证据找首次分歧和原本能更早发现它的节点，再试一个最小改变。能减少返工的节点保留；没有新增观测的重复检查可以合并。记录假设、调整、预期观察和实际结果，不自动把每次问题都转成新门禁。

比较旧/新策略时，区分文字场景推演、真实执行、控制变量的对照试验和实际项目观察。对照试验使用相同输入、代码基线、模型设置与可用工具，隔离执行上下文，执行者不读答案；记录无法控制的差异。小 bug、成熟功能和复杂 Goal 分组比较，多次样本后再判断，不用一次通过或耗时下降证明整体质量提升。
