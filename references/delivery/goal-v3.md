# Goal v3：按结果交付

适用于用户已授权实现、需要连续执行和恢复的 Goal。创建和恢复统一使用 schema 3；不提供旧格式执行或自动迁移。轻量修改不必建包。

## 开工与恢复

只维护两份常驻文件：`.goal/goal.yaml` 写结果约定和工作依赖，`.goal/status.yaml` 写任务进度与有序核验记录。一次核验用一份 `runs/*.yaml`，证据可以引用已有文件；不另建批次、验收状态、恢复计数或四种角色报告。模板见 `templates/goal-v3/`。

1. 读项目入口、用户最新决定及适用授权；默认当前目录与现有环境，核实实际差异和仍有文件/运行资源操作权的参与者。接任与运行核对按 `references/delivery/agent-delivery-flow.md`，不假设旧聊天常驻。
2. 读 goal、status 和当前结果的来源区块，运行 `ruby <playbook-root>/scripts/check-goal.rb <goal-dir>`。`passed_results` 只表示已审快照上的证据有效；出现未审差异或 `needs_impact_review` 时，主线程先判断影响，不能直接把历史通过套到当前代码。检查器不能判断预期或证据是否正确。
3. 按结果依赖选就绪任务。普通工作自测后记 `done`，不代表结果已验收。共享规则用 `kind: shared_foundation`；消费它之前，须有当前有效的独立核验。其他无依赖工作继续。
4. 先贯通最小真实路径，再扩展状态；首次贯通不自动触发 CR。普通结果可继续实现，相关结果按 `references/stages/review.md` 合批正式核验；一个 run 可检查多个结果，不增加批次状态。可隔离缺口不使全局停止，真实能力仍保留待验。
5. 检查器在创建/恢复、正式核验与收尾使用，不每步运行、捕获快照或建 run。阶段内已有检查且相关状态未变时复用；成本控制见 `references/delivery/execution-evidence.md`。

## 预期只写一处

每个结果写清入口、动作、对象、上下文、结果及一个能区分误解的反例。任务只引用结果编号，不重述产品要求。结果引用决定和可定位的来源区块；原型负责的局部结构、既有页面负责的外壳及允许差异必须具体写在来源里，不能用“沿用原页面”概括全部界面。

用户更新要求时，更新决定和受影响结果，递增 `revision`，再继续工作；旧原型不能覆盖新决定。发现来源冲突，主线程先按已确认目标和实际事实收口，或隔离受影响部分继续；不能靠文件时间或旧测试通过选择产品口径。确实缺少授权或不可获得的外部事实时，记录具体缺口和恢复条件，不自动重开产品问答或停止无依赖工作。

实现者可以自主决定组件、内部函数、工具、测试方法和满足结果的局部修复；不能自行改变入口去向、页面层级、数据归属、权限或已确认结构。复用已有授权，不因换人或恢复而重新索要。

## 派发与独立核验

中文短提示统一见 `references/delivery/agent-delivery-flow.md`，只传当前来源、最近决定、相关授权、事实、文件及运行资源范围；默认最小显式上下文。不要复制整份历史，也不要新建行动卡。

独立核验可由同一未参与该组实现的 Agent 完成行为验证和 CR；先从当前依据确定预期并观测，再读实现结论。身份字段不同不等于实际独立；主执行者裁决缺陷、误报及建议。

## 一次核验与增量复用

1. 固定包含未提交文件的快照。用 `ruby <playbook-root>/scripts/check-goal.rb --capture-v3 <goal-dir> <id>` 生成引用；将实际输出写进 run，不手造摘要。
2. 用 `ruby <playbook-root>/scripts/check-goal.rb --delta-v3 <goal-dir> <id>` 生成从上次 run 到已捕获快照的完整差异草稿；首次与基线比较。保持自动列出的完整文件清单，逐项补关联结果、行为变化或无行为变化及理由，不能将所有项预填 `no_behavior` 绕过判断。`from` 引用上次快照，首次为 `null`；`to` 为本次。
3. 对需要核验的结果记录 `contract_hash`、原始证据引用与实际观测。涉及运行现场时，在现有 `observed` 和证据中保留相关入口、实际构建/进程/数据配置事实、观察方法及时间；只写脱敏的必要信息，字段齐全不等于行为成立。预期来自结果和来源，不能由实现或旧测试反推。界面操作须运行验证，图片不能独立证明跳转；数据写入须从实际存储读回。
4. 独立 review 检查同一完整差异的影响，不把未就绪的独立结果当成必须同时验收。记录 `blocking_findings` 和各项 `passed / failed`；阻塞范围明确时用 `review.blocking_results` 列结果 ID，沿依赖使相关结果失效，无关检查仍可通过。数量大于零时显式范围不得为空或引用未知结果；范围不明时省略该字段，保守阻塞本轮受影响及核验结果，继续查清，不通过填空列表消除阻塞。把 run 文件摘要追加进 status，检查器按声明的影响使结果待核验或采用新证据；主线程仍须发现未声明的实际影响。未受影响证据可复用。修复后追加新 run，保留历史，不修改旧记录吞掉失败。

摘要将结果 revision、预期、所引用决定、来源文件和依赖纳入有效性判断，忘记递增 revision 也不能沿用变更前的口径。当前实现按**来源整文件**取摘要：同文件其他区块变化也会保守失效；要缩小影响可拆成自然独立的来源文件，不谎称已实现区块级摘要。摘要只能发现输入变化，不能证明预期准确或防止恶意伪造。

快照包含 Git 已跟踪文件和未被忽略的新文件；只支持本地普通文件，拒绝符号链接及子模块。配置输入只纳入项目批准的脱敏内容，不把 `.env` 或密码复制进证据对象；实际环境标识、配置版本写入观测。删除结果或降低 revision 需显式迁移审查，当前检查器拒绝直接改写。

## 完成

所有任务 `done`，全部必需结果有当前有效证据，完整差异无遗漏，才通过 `--complete` 检查并将 status 记 `complete`。发布、外部写入、真实付费调用仍按本次授权及项目 SOP；开发验收不能冒充已发布。本次已承诺的真实环境结果不能移到未来再验。

只在任务完成、用户变更、核验裁决或停止等恢复边界更新记录。最终说明结果、关键证据、未验证项与发布状态；不把检查器通过当作业务正确的证明。

需要跨上下文恢复时，在 status 可选写 `next_action`、`constraints` 来源、`active_workers` 文件/资源操作范围及 `open_gaps`，不复制另一份进度表。

`active_workers` 沿用 `id/task/state/write_scope`，可选 `resource_scope` 为项目内约定的资源标识列表（如 `local-api`、`local-jobs`）。同一实际资源统一标识；脚本仅拒绝重复标识，无法识别不同别名或阻止外部进程。`write_scope` 可以为空，但文件或资源操作范围至少一种非空。失联 `stale` 仍占范围；只读协作者无需登记独占范围。仍持有写权限的 worker 或必需缺口未收回时不能完成。任务的 `work` 只写工程动作，`self_check` 写最小检查方法，产品预期仍只引用结果。
