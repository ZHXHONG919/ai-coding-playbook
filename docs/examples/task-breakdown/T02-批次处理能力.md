# T02 批次身份、结果与恢复能力

> 类型：领域能力与执行协作；负责人：本组owner；关联R-submit/R-process/R-query/R-retention
> 依据：方案第3至8章，需求R-01至R-08；完整字段、枚举、索引和协议精确采用方案第4/5/6章。

## 目标与职责

批次应用服务负责创建或找回批次、参数冲突、查询归属与结果视图；执行模块负责领取、凭证、有限重试和过期恢复。审核合法性与审核记录调用T01，不在执行器重新实现。批次保存身份，条目保存领取和结果，不能把这些属性塞进Content。无界面变化，本任务的HTTP错误由T03消费。

## 行为与接口承接

POST /api/review-batches从认证取得提交人，以Idempotency-Key和规范化参数按方案去重：同人同标识同参数返回原批次202，不同参数409。创建和重放都不是审核完成。GET /api/review-batches/{batchId}检查当前权限和归属，不存在及他人批次统一404；已接收任务执行按提交时授权，不因当前权限撤销而取消。

执行模块从持久条目领取，以有效凭证调用T01；内容、审核记录和成功项同事务保存。每项独立；系统故障最多尝试3次，数据库不可写时保留恢复可能，不伪造失败已保存。查询用同一快照汇总条目，完成时间及外部PENDING映射引用方案，不把内部RUNNING暴露成新业务状态。

## 必要自测

V01：同人同标识同参数并发仅一个批次；换参数409；不同提交人的标识范围按方案独立。仅串行重复不能证明并发去重。

V02a（S05）：通过S03真实提交准备初态批次，从真实GET分别以原提交人、另一用户、撤权提交人查询，验证允许、404、403及初态汇总与明细一致；此时不证明真实执行或终态。

V02b（S04）：真实提交后撤销提交人权限，经正常worker入口执行并从存储读回结果，验证已接收任务仍按提交时授权执行；不依赖S05查询入口。S05完成后的查询拒绝另由V02a验证。

V02c（S04和S05均完成后的集成）：通过真实POST创建至少含两条待审内容的批次，先从正常GET确认初态。让真实worker处理其中一条，在真实GET读取期间协调该条事务提交：若查询分多次读取，先定位产生响应明细、汇总和完成时间的条目读取及受该提交影响的字段，在相关读取之间用测试同步点放行提交，必要时覆盖不同读取顺序；鉴权或批次元数据读取不能代替这些交错点。若使用单条SQL，需以数据库层面的实际观测证明语句快照建立、worker提交、语句执行完成的先后，或采用有依据的等效数据库验证；仅证明HTTP响应返回前发生提交不够。同步点仅控制时序，不替换查询、worker或数据库；使用现有开发库和明确标识的样本，不预填审核结果。

记录批次ID、实际相关读取及提交的先后、返回明细和汇总，再从存储读回提交后的事实。以返回明细逐项计算状态计数及完成状态，必须与同一响应的汇总、完成状态一致；有未完成项时 `completedAt` 为 null，全部终态时等于条目 `processedAt` 的最大值，即使批次完成快照尚未补写。响应可反映提交前或提交后，但不能将两者混合。例如先读到两条未完成、worker提交一条成功、再读到一条成功的汇总，应判失败。另从正常GET读取真实产生的混合终态，验证最终结果、汇总和完成时间。未能证明相关读写实际交错时，该次只证明普通读回，保留并发快照检查缺口，不能凭多次轮询或终态一致宣布通过。

V03：处理中停止有操作权的执行进程，租约到期后恢复；旧凭证不能再写，已完成项不重审。连续系统故障3次转系统错误，其他项继续；数据库不可用时不伪报终态。与T01共享事务证据，不重复做一套审核测试。

V04：使用时间边界样本验证未完成及90天内结果保留、到期完成结果可清理，审核记录不随批次清理；保留范围和去重窗口一致。

验证前确认现有开发库连接和脚本建库/清库行为，不自行新建或切换数据库；故障和清理验证不得破坏既有业务数据，不能安全执行的检查保留缺口。任务自测不代替T03用户路径及完整质量验收。
