# T03 批量审核提交与结果查看

> 类型：用例功能；负责人：本组owner；关联R-submit/R-process/R-query
> 依据：方案UC-01/UC-02、API-01/API-02；需求R-01至R-07及A-01至A-06。

## 目标与边界

审核人员从已有内容列表选择、确认提交、进入结果页，并能刷新或从保存地址恢复同一批次。页面和HTTP入口组织调用，不自行判断内容是否还能通过。所有共同规则由T01/T02承接；本次不增加历史批次列表或取消任务。

## 具体交互与编排

| 操作/条件 | 输入来源及请求 | 输出与反馈 |
| --- | --- | --- |
| 选择并确认 | 本租户列表选择1～100项；确认生成请求标识，POST API-01 | 202后由batchId进入/review/batches/{batchId}，显示处理中，不显示审核成功 |
| 响应丢失/5xx | 原标识及原参数重试 | 找回同一批次；409不自动换标识，400/403按协议提示 |
| 查看、刷新、历史返回 | 从页面地址读取batchId，GET API-02 | 使用服务端条目和汇总，不能用本地选择推测处理结果 |
| 未完成/全部终态 | 未完成每2秒查询；30秒未完提示沿方案原文 | 终态后停止轮询，完成不等于全部成功；请求失败保留已显示结果并允许重试 |
| 主动重提失败项 | 返回列表重新选择，以新的用户意图生成新标识 | 新批次，不能把主动重提混成原请求网络重试 |

加载、空态、提交中、禁用/取消、关闭及返回的视觉和交互细节须由采用原型明确，不能因本表未写而擅自补产品规则。成功、业务失败、系统错误、无权限和不可访问均按API区分。

开发与恢复实际打开已确认固定图片；缺图回原型准备，不由本任务执行者自行截图采用。图片约束画面，原型约束操作，方案约束业务与请求；允许差异须有采用依据，不能覆盖旧图消除差异。

## 完成条件与自测

V01：真实选择3条，其中一条已通过，提交202后先显示处理中，最终2成功1业务失败；读回内容、记录和结果，不用预填终态证明处理成立。

V02：模拟响应丢失并原样重试，观察只有一个批次；换参数同标识409且页面不偷偷换标识。更改服务端模拟条目/汇总后页面随响应变化，检出前端自造结果。

V03：实际观察轮询、超过30秒提示、终态停止及查询失败后保留结果；刷新与历史返回读取地址中的同一批次，不能依赖浏览器内存才恢复。

V04：另一用户和撤权提交人访问，按404/403处理；视觉对照固定图片，点击/关闭/返回及请求触发须实际操作，图片不替代。业务与数据库检查复用T01/T02有效证据，但完整用户路径仍要真实跑通。

当前缺口：原型及图片由原型准备方补齐并采用；方案仍待评审。仅相关无依赖准备可继续，本组不能宣布已可执行前端或真实后端。
