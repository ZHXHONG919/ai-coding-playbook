# 任务拆解节点：规则、模板与案例

本次将任务拆解明确为采用方案与执行之间的承接节点。方案确定领域职责、用例行为及存储/接口；任务文档落实具体工作、能力调用、依赖与判错检查，Goal维护结构化结果和唯一执行进度。

## 使用入口

- [任务拆解规则](../../references/plan/task-breakdown.md)：输入、职责、拆分方式、完成标准和上下游交接。
- [目录模板](../../templates/tasks/README.md)与[任务正文模板](../../templates/tasks/task.md)：统一骨架，按领域能力或用例功能展开。
- [贯穿案例](../examples/task-breakdown/README.md)：承接新版批量审核方案，展示共同审核能力、批次能力及提交/结果查看用例，以及工程步骤到Goal的映射。
- [回归场景](../../evals/plan/task-package-domain-and-ui.md)：检查职责复用、具体任务、固定图片、局部缺口和授权边界。

任务目录不要求一文档对应一个Goal工程任务，也不要求先写完全部真实领域实现再做前端。依赖落到契约、模拟、完整前端体验、真实能力与集成步骤。普通小改和已有tasks.md继续使用，不强制迁移。

界面任务明确自己的原型采用版本、入口、UI Flow节点、状态、固定图片与比较条件。图片、可操作原型、业务契约各负其责；缺图回原型准备，不由实现者自行截图采用。案例输入没有实际采用原型/图片，已明确列缺口，不虚构基准，不声称可执行界面或业务验证完成。

Goal保持schema 3，work/self_check引用任务步骤与检查项，depends_on表达真实依赖，结果sources/decisions保留实际产品和界面来源。任务摘录带来源的必要行为，不另立业务决定；状态只在status维护。方案、交接、实现、Goal恢复入口均已接通。

## 验证与限制

`bash scripts/check-playbook.sh --repo-only`通过：57项测试、458个断言、32组既有行为场景的结构检查；本次新增模板、案例和规则的本地链接及git diff空白检查通过。结构检查不表示32组行为均通过，也不证明真实项目交付效率已提高。独立文本场景回放记录见[本次记录](../../evals/plan/task-package-replay-20261023.md)。

发布采用功能分支提交、推送并通过PR合并main；本地随后同步并切到main。本仓库发布的是可复用规则，无业务服务部署、数据库变更或额外版本标签。已有全局goal-execute为本仓库软链接，其正文随源文件更新可见，无需重复运行安装脚本。回退时通过新的PR撤销本次变更。
