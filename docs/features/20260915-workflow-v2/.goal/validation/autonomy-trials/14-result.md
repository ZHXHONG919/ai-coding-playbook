> - D2：这是采用稿落地，不能改布局和关键控件。唯一采用稿为 UI-7，其真实来源是项目 `docs/feature/prototype/README.md`。请先实际打开该文件及其指向的采用稿，读取版本、页面状态、1440px 参考视口和允许的框架外壳差异。主线程目前没有打开该来源，不能把这条交接当成已核验采用稿。
>
> **事实与范围**
>
> - 当前代码版本 V7。真实上传器提供 `assetId: UUID`、`ready: boolean`、`busy: boolean`；预览服务消费 `assetId`。先在代码中定位真实生产者、类型和消费者，不编造路径或协议。
> - 输入协议任务 T2 已 `implemented`，与 T3 同属 B02，可继续本批次实现；这不代表 T2 或 B02 已独立验收。
> - 你只改预览面板及相关行为测试。不改上传器、预览服务、共享权限、其他 Worker 文件或 `status.yaml`。共享规则有问题交主线程裁决。
>
> **实现与最小自测**
>
> - 优先复用采用稿结构、样式和组件，再接真实数据。首个可运行面板按 1440px、相同状态对照采用稿，校准后再扩展。
> - 通过实际面板操作进入应用预览路径，观察面板状态、触发时机、调用次数及传入的 UUID。至少覆盖：
>   1. 上传完成但未确认补充结束：仍保留继续补充的询问，不自动预览。
>   2. `ready=true`：用户可手动预览，传入真实 `assetId`。
>   3. 明确补充结束：就绪后按 D1 自动预览，不能提前跳转。
>   4. `busy` 与 `ready` 的相关组合，以及重复点击：状态展示、操作条件符合采用稿和 D1，不重复触发同一次预览；不能擅自用忙碌状态增加产品限制。
> - 可替换外部上传供应方，但必须保留应用内部状态判断和预览执行。不能手造应用内部预览结果证明成功。
> - 输入或采用稿缺失时，报告具体事实、影响与可独立推进范围，不自行画近似界面或改产品流程。
>
> **返回要求**
>
> 返回修改文件、实际代码版本、自测输入／预期／运行观测与证据、未覆盖项及下一步可用范围。视觉还原、交互一致、业务正确分别说明。构建通过不能证明完整还原。
>
> 自测有效通过后由主线程记录 T3 `implemented`；B02 后续在同一固定版本上独立验证与 CR，通过后才验收。

## 2. 对“编译通过且改成上传完自动预览”的裁决

**退回修复，T3 当前不能算实现完成，B02 不能验收。**

两项问题分别处理：

- **违反 D1：** “减少点击”是 Worker 自行提出的产品变更，不能覆盖已确认流程。恢复上传后询问、就绪可手动预览、明确补充结束后才自动预览。
- **证据不足：** 编译通过只能证明对应构建检查通过，不能证明视觉还原、交互一致或业务正确。

主线程直接下发上述定向修复，无需重新询问用户。Worker 补验原失败路径、busy／ready／补充结束／重复点击及受影响界面状态。保留未受影响的改动与有效证据，不要求重做整个批次。随后固定修复后的代码与契约版本，安排 B02 独立验证和 CR；核验者先从 D1、D2 和真实入口推导预期，再读实现报告。

## 3. 无法打开 UI-7 来源时

先报告打不开的具体路径、错误及已做的有限检查，由主线程定位正确来源或解决访问缺口；不能声称看过 UI-7，也不能擅自换一份近似稿。

仍可推进：

- 核实 V7 的上传器类型、UUID 和预览消费者。
- 实现不依赖未知视觉细节的本地状态逻辑。
- 基于明确的 D1 编写并运行行为测试，接通可运行的真实应用路径。
- 整理已知交互与尚缺采用稿依据的部分。

暂不推进依赖未知采用稿的布局和关键控件变更，不扩散未经对照的布局。由主线程在现有记录中登记缺口、负责人、恢复条件及回收点；来源恢复后实际打开，并完成同视口、同状态校准。

行为逻辑可分别记录已验证范围，但 T3 的采用稿还原仍待验收，B02 不能据此宣布完整完成。局部视觉缺口不阻止其他独立工作。
