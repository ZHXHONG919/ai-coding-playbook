# 08 普通任务与基础规则

我按 ai-coding-playbook 进入连续执行安排阶段。采用输入已有的 functional_batch 与 continuous，不把 A 的普通任务边界变成暂停点；B、C 在其依赖开始前分别完成基础规则验收。

## 执行顺序与边界

| 工作 | 判断与下一步 |
| --- | --- |
| A：只改必填提示，自测已通过 | 记 implemented、保留自测证据，继续可执行任务。调用未改变的权限服务不构成基础规则变更，不单独升级成权限专项 CR。A 等所属功能批次闭合后统一验收。 |
| B：改变共享审核状态 | 明确新旧状态转换及提交/批准等消费者，单列有限范围 foundation 批次、before_dependents。实现和自测后固定版本做独立验证及专项 CR；批次 accepted 后，依赖该状态的提交/批准任务才可开始。 |
| C：改变共享计费扣减 | 明确扣费时机、身份/额度、重复请求和失败恢复规则，单列 foundation 批次、before_dependents。有效自测、独立验证和专项 CR 通过且 accepted 后，依赖它的生成任务才可开始。 |

B、C 不能与依赖方一边猜规则一边并行实现。若二者代码和契约独立，可由主线程明确各自 owner 后并行，或在等待 B 审查时推进 C；若存在依赖则按实际依赖顺序。核心状态和计费判断由主线程掌握，不把两者塞进一个无限扩大的基础批次，也不要求每个小任务完整 CR。

## 验证范围

A 复用实际表单文案/必填显示的检查即可，除非发现权限行为也变更，不重验整套权限服务。

B 从真实提交/批准入口覆盖改变后的合法转换、禁止转换以及本次触及的重复/恢复行为；C 从实际扣费入口观察余额和记录，覆盖合法扣减、重试不重复扣减及已确认的失败处理。涉及事务/并发正确性时使用合适的本地数据库证据，不以 mock 余额或接口 200 替代。具体规则和命令必须从已确认契约及代码取，不在此猜测退款策略。

## 继续与完成判断

A 完成自测后立即继续；B/C 的基础验收只阻止依赖其规则的任务，不阻止可隔离工作。功能批次真正可操作后，在固定版本集中独立验证和 CR；验收通过、当前阻塞清零才记 accepted。最后还要核对所有批次、最终增量和完整用户成功场景，才宣布整个请求完成。批次通过后 continuous 自动进入下一项，不反复询问是否继续。

输入未给 B/C 的确认规则、批次映射和实际依赖，因此可确定审查边界，不能直接宣布它们设计 Ready 或承诺并行安全。读取已有契约解决；只有无法从事实解决的高影响未知才暂停其受影响工作。

## 使用的规则与矛盾

使用候选入口、交付流程、Goal Execute、实现、Review、任务拆解与测试范围规则。输入写 run_mode，而 Goal 文档配置字段为 run_control.mode；应核对项目实际字段与语义，不静默改名。README 的复杂长链路必建 Goal 与核心规则按恢复需求/用户请求决定的口径存在差异；此场景已有执行策略，不因该差异新增 Goal 或迁移。
