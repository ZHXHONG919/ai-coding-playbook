# 02 业务产物决定验收

我按 ai-coding-playbook 进入批次验收阶段。**当前批次不能完成**：页面、health、单测和预选名称展示，均未证明审核内容经过发布后进入最终提示词。

## 最少补充验证

固定当前版本，用一份内容可辨认、预期独立于实现的预选，从实际审核/发布入口执行：

`预选审核通过 → 发布内容包 → 同一存储读回 → 实际编译入口 → 读取最终提示词`

- 内容包必须由被测发布逻辑产生，核对其审核来源、正式内容和关联关系；不能只断言名称，也不能手工预填最终内容包。
- 用读回的包触发真实编译，核对已确认应进入提示词的内容、规则或参数确实出现，并且没有选错来源、漏内容或残留未解析引用。预期取自固定样例和业务契约，不由本次编译函数生成。
- 若编译后的提示词还会被请求装配改变，继续观测图片供应商调用前的最终请求；在供应商边界截获即可，本轮不调用图片供应商。
- 用一个相关反例证明检查能检出问题，例如同名不同内容样例被换入，或人为断开编译输入后，最终内容断言应失败。审核拒绝分支仅在本批次改变/承诺该规则且既有证据不足时补测。

这是一条贯通应用逻辑的短路径，可复用已有 UI 入口和测试设施。不重复跑已可信的 health，也不把大量孤立单测数量当作补足。

## 继续与完成判断

补验失败则定位发布、持久化、读取或编译的实际断点，修复后定向复验；无依赖工作可继续。最终提示词验证通过、固定版本独立 CR 无阻塞且批次验收项均有证据，才可记 `accepted`。本轮无需图片生成质量证据，因为图片供应商调用明确不在范围内。

输入缺少编译契约、完整验收清单及 CR 版本，因此不能承诺补一条断言后整个批次必然完成，也不能凭预选名称猜测正确提示词全文。

## 使用的规则与矛盾

依据候选入口、交付流程、`skills/test-scope-analysis/SKILL.md`、`references/delivery/evidence-driven-delivery.md`、`references/stages/review.md`、`references/scenarios/ai-media-pipeline.md`。Provider Skill 的通用验证顺序包含真实调用；本场景的明确“不调用图片供应商”限定优先，不据此扩大验收。
