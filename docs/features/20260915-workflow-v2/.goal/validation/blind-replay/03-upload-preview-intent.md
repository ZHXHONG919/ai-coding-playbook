# 03 保留上传后的用户意图

我按 ai-coding-playbook 进入最小修复阶段。保留三条已确认规则：资料齐全即可手动预览；上传后继续询问补充；用户明确没有补充才自动预览。

## 最小修复方向

核实上传成功、失败及预览点击的真实控制流，修复该上传操作对应的 loading 收尾，并保证成功返回的完整方案成为后续读取的数据。按项目异步状态机制处理成功/失败的终结状态；不能仅在某一成功分支清理，留下失败后永久忙碌。

同时检查预览 guard 的实际条件和读取时机：去除因遗留 loading 或旧闭包造成的误拦截，保留必填/图片等已确认校验。若为 React 等异步状态更新，不能假定 `setLoading(false)` 后同一回调立即读到新值；应使用一致的新数据/完成状态触发相应行为。

上传成功只进入“询问补充”，不直接调用自动预览；明确无补充才走自动预览。不能新增“先回答无补充才能手动预览”的限制，也不凭工程直觉增加其他禁止条件。

## 自测范围

| 实际操作 | 预期 |
| --- | --- |
| 上传成功，方案必填与图片齐全，尚未答复补充 | loading 收尾，显示补充询问，不自动跳转 |
| 上述状态点击主动预览 | 使用最新完整方案进入预览，不被遗留 guard 拦截 |
| 明确没有补充 | 自动进入预览，不因旧状态漏触发或重复触发 |
| 明确还要补充 | 保留补充流程，资料齐全时仍允许主动预览 |
| 必填/图片不足，或上传失败后重试 | 不足时遵守原校验；失败时忙碌状态归还、显示原定错误反馈，可重试且不误自动预览 |

通过实际客户端运行态验证这些状态，复用已有交互测试；重点保留“上传成功 → 点击预览”这一原失败路径证据。若共享 loading/预览函数还被其他入口使用，补查其直接消费者。没有影响扩大的证据时不跑整库回归、不重新设计原型。

## 继续与完成判断

可以继续最小修复，不需要重新确认已经明确的交互。实际自测通过后进入受影响范围独立验证/定向 CR，证据对应最终修改版本才收口。输入未给源码和状态框架，以上是修复方向，不是已确认的具体代码根因；不能承诺简单添加一个 finally 就一定解决全部 guard 问题。

## 使用的规则与矛盾

使用候选入口、交付流程、实现、排障、测试范围、交付证据和 Review 规则。`bugfix.md` 的收尾全量回归默认条件比证据规则更宽；本例采用可明确界定影响范围的局部复验。完整差异记录见 `_reading-log.md`。
