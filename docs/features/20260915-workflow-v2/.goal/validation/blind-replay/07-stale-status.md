# 07 状态不能代替当前代码

我按 ai-coding-playbook 进入 Goal 恢复与最终收口阶段。**C2 的 accepted 不能证明当前 C3 已验收**。C3 新增上传状态运行逻辑没有修改后的验证和定向复审，当前受影响批次应视为待验收，聊天中的“全部完成”无效。

## 先核实并恢复真实状态

1. 读取现有 Goal 的状态、批次映射、gate、验收和 C2 证据，再对照当前实际文件。除 C2→C3，还核对未提交/新增文件；快照不能只记 HEAD。
2. 明确上传状态增量影响哪些任务、消费者、UI 状态及已验收结论。受影响批次由 accepted 回到 pending；保留 C2 证据及其版本范围，未受影响的结论可复用。
3. C3 任务若有适合该改动的有效自测证据才可记 implemented；输入未给出，不能直接假定已自测通过。先补自测并记录真实结果，必要时保持 in_progress。撤销受影响的整体 code_complete/complete 结论，恢复 current/next 指向具体补验补审动作。
4. schema_version 已为 2，不触发旧 schema 迁移；仍须核实实际 review_strategy、run mode 和 gate，不能凭字段版本猜测全部执行契约。

## 收口验证范围

从实际上传入口检查 C3 改变的成功、失败、忙碌复位以及直接依赖状态的后续操作，预期以最新用户交互约束为准。不能仅重放不覆盖新逻辑的 C2 测试。

补完自测后固定当前版本，让独立验证与定向 CR 在同一快照检查 C2→当前的运行增量和影响域。若需修复，更新版本，仅失效并补验受影响结论。最终从 Goal 原始基线到交付版本核对完整差异、各批次覆盖、契约变化和未完成项，避免只查上传一个文件而漏掉其他增量。

## 继续与完成判断

“请继续收口”足够授权继续已知收尾工作，不因历史已完成或普通批次边界停下，也不自动提交、推送或发布。只有当前版本的所有承诺验收、必需 CR 与最终覆盖均通过，才恢复 accepted 和整体完成。无影响证据可复用，无须重做所有 C2 检查。

本次评估不实际改写 `.goal`。输入没有真实差异、报告和业务约束，因此目前只能确定“验收结论过期”，不能确定新代码有缺陷、具体测试命令或剩余工作量。

## 使用的规则与矛盾

使用候选入口、交付流程、`skills/goal-execute/SKILL.md`、实现、Review、测试范围、交付证据和任务拆解规则。状态、代码与证据的优先关系在这些核心规则中一致。若按排障路由处理上传，仍有全量回归措辞张力；此处不以 Goal 身份自动重跑全仓。
