# Design Discussion Rules

> 用于约束多轮技术方案讨论。目标是让方案越聊越清楚，而不是每轮都产生一段新的散文。

## 1. 维护“当前共识”

多轮讨论中，每次用户提出质疑或新判断后，回复必须显式更新当前方案状态。

建议结构：

```markdown
## 当前共识更新

- 已确认：...
- 本轮修正：...
- 仍待确认：...

## 回答你的问题

...

## 对方案的影响

- 模型变化：...
- 流程变化：...
- 待更新点：...
```

要求：

- 不要每轮像第一次回答一样重新发散。
- 用户纠正后，要明确“我前面哪里说得太泛 / 太硬 / 不准确”。
- 方案概念变化时，要说明旧方案如何被替换。

## 2. 术语引入协议

不要直接抛出新名词。引入新概念时必须说明：

| 项 | 要说明什么 |
| --- | --- |
| 中文名 | 运营/产品能理解的名字 |
| 英文/代码名 | 可能的实体或类型名 |
| 它是什么 | 一句话定义 |
| 它不是什么 | 避免和相近概念混淆 |
| 为什么需要 | 没有它会有什么问题 |
| 生命周期 | draft / analyzing / approved 等 |
| 与已有概念关系 | topic、content_pool、preset、pack 等关系 |

如果用户问“这是什么”，说明前一轮术语引入失败；下一轮要先补定义，再继续设计。

## 3. 用户质疑优先于自洽

当用户提出“我感觉不是这样”“为什么”“是不是应该”时：

1. 先判断用户质疑是否成立。
2. 如果成立，明确承认并修正，不要维护原答案。
3. 如果不完全成立，给出适用边界，而不是直接否定。
4. 更新当前决策表。

示例：

```markdown
你这个质疑成立。我前面把内容池设计成多对多，是偏平台化；按当前业务，一期应收敛为 topic 与 content_pool 一对一。
```

## 4. 维护决策表

复杂方案每 2-3 轮应该输出一次决策表，避免概念漂移。

| 决策点 | 当前结论 | 原因 | 是否已确认 |
| --- | --- | --- | --- |
| 内容池与主题关系 | 一期一对一 | 内容池需要清晰边界 | 用户已确认/待确认 |
| 分析结果形态 | 可运行 draft，而非只看 suggestion 文案 | 审核需要试跑效果 | 已修正 |
| pack 入口 | Pack-first / Topic-first | 贴合运营心智 | 待确认 |

## 5. 输出要推动下一轮讨论

方案阶段每轮最后不要只结束在“所以一句话”。要给出下一步可讨论点。

```markdown
## 本轮需要你确认

1. 内容池和 topic 是否按一对一收敛？
2. analysis_pack 是否作为一期核心工作单？
3. draft 审核是否以“试跑单条笔记结果”为准？
```

## 6. 避免过早实体化

在模型还没讨论清楚前，不要一上来列很多表名。先确认业务概念，再落实体。

顺序：

```text
业务概念
→ 概念边界
→ 概念关系
→ 生命周期 / 状态
→ Entity / 表字段
→ API / 页面
```

如果用户还在问“内容池和主题是什么关系”，就不要急着设计 `sync_record`、`external_snapshot` 等外围表。
